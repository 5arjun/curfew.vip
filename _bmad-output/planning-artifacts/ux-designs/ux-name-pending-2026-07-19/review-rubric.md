# Spine Pair Review — Curfew

## Overall verdict

Curfew's spine pair is directionally strong — token discipline, voice, and flow fidelity to the PRD all hold up well, and nothing found here blocks a first implementation pass. But it isn't the "no misses" bar the mechanical rubric asks for: roughly 40% of named components have a one-sided visual/behavioral gap, three of eight IA surfaces carry zero State Pattern coverage, and neither spine links back to the eight already-rendered Stitch screens that would resolve several of these gaps for free. Most notable: the energy-arc and trend charts — the product's actual differentiator and the climax mechanism in two of the four Key Flows — have no DESIGN.md visual spec at all. The prior automated pass's "non-blocking, will resolve at mock time" framing is largely fair for the smaller items, but undersells the chart and visual-reference gaps, and the artifacts' own `status: draft` frontmatter (never flipped to `final`) is honest about where this actually stands.

## 1. Flow coverage — adequate

Checked: every UJ named in PRD §2.3 against EXPERIENCE.md `Key Flows`. Phase 1 UJs are UJ-1, UJ-3, UJ-5, UJ-6, UJ-7; Phase 2 UJs (UJ-2, UJ-4) are correctly out of scope per `Foundation`'s explicit Phase-1-only framing and absent from EXPERIENCE.md entirely — no drift there. UJ-1, UJ-3, UJ-5, UJ-6 each have a named-protagonist flow with numbered steps, a **Climax**, and a **Resolution**; UJ-3 additionally has an **Edge case** (failure path). UJ-1 and UJ-3's failure/edge paths are present; UJ-5 and UJ-6 have no failure path, but neither PRD journey describes one to inherit.

### Findings
- **low** UJ-7 (wedding client-request mismatch) has no Key Flow (`EXPERIENCE.md`, no `### UJ-7` heading). Independently verified this is defensible, not an oversight masked by the memlog's framing: UJ-7 realizes only FR-6 and FR-16, both already exercised by UJ-1's flow and the generic `Layer 2 form` Component Pattern row, and it introduces no new screen, component, or interaction. *Fix:* none required; optionally add one sentence to `Inspiration & Anti-patterns` or a footnote noting the deliberate scope-down, since nothing currently documents the decision to skip it.

## 2. Token completeness — adequate

Checked: every `{path.to.token}` reference in both files' prose against frontmatter (see Mechanical notes for the full extraction) — every reference resolves, no broken cross-refs. All 48 color tokens carry hex values. No light/dark pairs needed (product is dark-only by explicit design constraint, stated in `DESIGN.md.Colors`).

### Findings
- **low** No numeric contrast ratios stated anywhere, beyond a prose note flagging the focus-ring glow (~20% opacity) as "worth a dedicated check" (`EXPERIENCE.md` Accessibility Floor). Independently checked several load-bearing pairings (`on-surface` #e2e2e3 on `surface` #121415; `on-primary-container` #330a90 on `primary` #cbbeff) — these read as comfortably AA-safe by inspection, and the palette is a Material 3 tonal export, which is contrast-safe by construction between `on-X`/`X` pairs. This lowers the risk but doesn't eliminate it — the focus-glow-at-20%-opacity case specifically is a genuine open question since a translucent overlay isn't a standard M3 on/container pair. *Fix:* run the stated focus-ring check before ship; otherwise low priority.

## 3. Component coverage — thin

Checked: every component name in `DESIGN.md.components` (frontmatter) + `DESIGN.md.Components` (body) against `EXPERIENCE.md.Component Patterns`, in both directions. Of ~17 distinct components named across both files (excluding the agent tray icon, deliberately native-chrome and out of `DESIGN.md`'s scope by design), 7 have a one-sided gap.

### Findings
- **high** `Energy arc chart` and `Trend chart` (`EXPERIENCE.md` Component Patterns rows) have no corresponding `DESIGN.md.Components` row — only `chart-summary`, the caption line that sits *beneath* the chart, is specified. Nothing in `DESIGN.md` governs the chart's own line color/stroke, baseline-comparison treatment, hover/tap annotation style, or axis typography. This isn't a cosmetic gap: the energy-arc chart is the product's named differentiator, and its gap ("EDM under-represented," UJ-1) and the trend line ("BPM range widened," UJ-5) are the literal **Climax** beat in two of the four Key Flows. The Stitch reference (`imports/.../curfew_set_detail_sticky_nav/code.html`, lines ~186–194) already renders a specific answer (`stroke="#cbbeff"` i.e. `{colors.primary}`, dashed `{colors.outline-variant}` baseline) that could be promoted into `DESIGN.md` almost mechanically. *Fix:* add an "Energy Arc / Trend Chart" row to `DESIGN.md.Components` specifying line color (`{colors.primary}`), baseline/comparison treatment, and annotation typography, sourced from the existing Stitch render.
- **medium** `Segment editor` (`EXPERIENCE.md` row: draggable dividers over the energy arc) has no `DESIGN.md.Components` row. Independently confirmed via the Stitch Set Detail render that no draggable-divider treatment exists there either — this one genuinely has no visual precedent anywhere yet, unlike the chart gap above. *Fix:* fine to defer to key-screen-mock time as the prior pass suggested, since there's no existing reference being left un-promoted.
- **medium** `New-set nudge` (`EXPERIENCE.md` row: inline banner, Add/Skip) has no `DESIGN.md.Components` row. This carries more risk than a typical missing-row gap: `Voice and Tone` is explicit that this nudge must read as "quiet, declinable" (never "push-style urgency"), so a banner built without a documented visual spec risks a downstream default toward an alert/warning treatment (e.g. reaching for `{colors.error}`) that would directly contradict the stated register. The Stitch dashboard render (`imports/.../curfew_dashboard_sticky_nav/code.html`, lines ~99–109) already shows a specific, non-alarming treatment. *Fix:* add a one-line `DESIGN.md` row: composed from `card-reflection`-tier surface + `button-secondary`/`button-primary`, no error-family color — cheap to close given the reference already exists.
- **medium** `avatar` (`DESIGN.md` frontmatter token, referenced once in `Shapes` prose as a `{rounded.full}` exception) has **no** `DESIGN.md.Components` body row and **no** `EXPERIENCE.md.Component Patterns` row — the only mention anywhere is `EXPERIENCE.md`'s IA table ("Profile / Settings | Nav (avatar)"). This is a two-sided miss the prior pass's memlog entries didn't surface at all. *Fix:* add a short `DESIGN.md.Components` row (size, border treatment already implied by the token) and an `EXPERIENCE.md` row for its one behavior (click → Profile/Settings).
- **medium** `Set-List Module` (`DESIGN.md.Components`, full visual row) has no matching `EXPERIENCE.md.Component Patterns` row. Independently verified via the Stitch Set Detail render (`imports/.../curfew_set_detail_sticky_nav/code.html`, lines ~334–380) that this is a real, already-rendered, interactive component — a "View Full Tracklist" button and timeline-style track rows — not a placeholder, so this is a genuine behavioral-spec gap rather than a component that's still purely aspirational. *Fix:* add a Tracklist/Set-List row to `EXPERIENCE.md.Component Patterns` per the memlog's own next-step note (per-track click behavior, "Unknown" track rendering per FR-2, "View Full Tracklist" destination).
- **medium** Auth form's WebAuthn/passkey option (`EXPERIENCE.md` row, `[ASSUMPTION — PRD sync owed]`) has no dedicated `DESIGN.md.Components` row for its visual treatment. Confirmed via `imports/.../curfew_signup_dark_theme/code.html` (lines ~147–161) that a specific "Biometric Anchor" treatment (bordered row, fingerprint-icon badge, two-line label, hover-fill radio indicator) is already rendered and just not promoted — same situation as the nudge banner above, a real gap but a cheap one to close since nothing needs inventing. *Fix:* add a `biometric-anchor` (or similar) row to `DESIGN.md.Components`, sourced directly from the cited file.

## 4. State coverage — thin

Checked: all 8 IA surfaces (`Landing`, `Login / Signup`, `Dashboard`, `Set Detail`, `Style Evolution`, `Library Utilization`, `Profile / Settings`, `Agent tray`) against `EXPERIENCE.md.State Patterns` for empty/cold-load/error/offline coverage.

### Findings
- **medium** `Landing`, `Login / Signup`, and `Profile / Settings` have **zero** State Pattern rows — no cold-load, no auth-failure (wrong password, existing-email-on-signup), no settings-save states, despite the product being explicitly framed as "consumer-stakes" in `Accessibility Floor`. `Dashboard` and `Set Detail`, by contrast, are thoroughly covered (6 and 2 rows respectively). *Fix:* at minimum, add an auth-failure row to the Failure Register (it already covers sync/drive/format/chart failures in the same console vocabulary — an auth-failure line is a natural, cheap extension) and a settings-save-confirmation row.
- **medium** `Style Evolution` has zero State Pattern rows despite UJ-5's Key Flow depending on trend data existing ("sees BPM range widened over the past month") — no defined state for a DJ with less than a month of history, who would hit this surface with nothing to show. *Fix:* add an "insufficient history" state, likely reusing the cold-dashboard pattern's tone ("Two more sets and Style Evolution has something to show you" or similar, in-register with the console voice).

## 5. Visual reference coverage — thin

Checked: all files in `imports/` (11 files across `stitch_curfew_dj_reflection_platform/` plus `inspiration-references.md`) against inline references in both spines.

### Findings
- **high** Neither spine links to any of the 8 rendered Stitch screens (or the raw `curfew/DESIGN.md` token source) inline at the relevant section. `DESIGN.md`'s frontmatter `sources` carries one generic line — "imports/stitch_curfew_dj_reflection_platform/ (Google Stitch design handoff, 6 of 8 Phase-1 screens rendered + generated DESIGN.md)" — that names the folder but not which file illustrates which surface, and doesn't distinguish the accepted `curfew_set_detail_sticky_nav/` from the rejected `curfew_set_detail/` sidebar variant, or flag that `curfew_dj_archive_flow/` is a byte-identical duplicate of the landing page. `EXPERIENCE.md` references `imports/` **zero** times — not even in its IA table, where 6 of 8 surfaces map directly to a specific rendered screen. Both example shape files (`design-example-mobile.md`'s pair, `experience-example-shadcn.md`) carry a `→ Composition reference: ...` line in the IA section naming specific files per surface — Curfew's EXPERIENCE.md has no equivalent anywhere. Compounding this: **no "spines win on conflict" statement exists anywhere in either file** (both example pairs state this explicitly). Concretely, this already matters: the Stitch chart render uses a literal hex (`#cbbeff`) with no stated resolution rule for whether that or the token wins if they ever diverge; two of the "genuine gap" findings above (energy-arc chart color, biometric anchor, new-set nudge) are only knowable *because* this review went and read the Stitch files directly — a downstream consumer working from the spines alone would not find them. `reconcile-stitch-screens.md` and `reconcile-inspiration-references.md` are thorough and honest, but they're working-audit docs, not part of the spine pair a downstream consumer is told to treat as canonical. *Fix:* add a `→ Composition reference:` line to `EXPERIENCE.md.Information Architecture` per surface, naming the specific accepted Stitch folder (and explicitly noting the rejected/duplicate ones so they aren't mistaken for live references), plus a one-line "DESIGN.md/EXPERIENCE.md win on conflict" statement.

## 6. Bloat & overspecification — adequate

Checked: pixel specs vs. tokens, source restatement, prose-where-table-works, decorative narrative untied to a decision, sections no consumer would read.

### Findings
- **low** ~30 of the 48 frontmatter color tokens (`secondary`/`tertiary` families, all `*-fixed`/`*-fixed-dim` variants, `inverse-*`, `surface-dim`, `surface-bright`, `surface-variant`, `background`/`on-background`) are inherited wholesale from the Stitch-generated M3 export but are never mentioned in `Colors` prose or any `Components` row — undocumented surface area in a system whose stated identity is "restraint is the point" (`Brand & Style`). Not a functional problem (unused tokens don't break anything), but it works against the system's own editorial discipline and a downstream consumer has no way to know if `secondary`/`tertiary` are reserved-for-later or dead weight. *Fix:* either prune to what's used, or add one line to `Colors` noting the rest are inherited scaffolding, not in active use.
- No other findings — DESIGN.md's editorial prose is tied to real decisions throughout (e.g. the `{rounded.full}` mis-export correction, the serif-glitch correction are load-bearing history, not narrative filler); EXPERIENCE.md stays disciplined and tabular, consistent with the shape examples.

- **Naming consistency:** no name collisions or drift found between frontmatter component keys, DESIGN.md prose headers, and EXPERIENCE.md references, beyond the coverage gaps already listed above in §3.
