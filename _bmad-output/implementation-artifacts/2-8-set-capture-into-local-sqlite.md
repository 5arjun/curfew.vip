# Story 2.8: Set capture into local SQLite

Status: done

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As a DJ,
I want completed sets captured and stored durably in local SQLite via the Epic 1 engine,
so that my sets survive offline and are available to sync and backfill.

## Acceptance Criteria

1. **Given** a completed Serato session with no DJ action, **When** detected, **Then** the agent runs the Epic 1 parse/enrich/stat engine — Story 1.3's `.session` parser or Story 1.3b's `master.sqlite` reader, per Story 2.6's source selection — and writes the result + retained raw to local SQLite. *(FR-1, AR-3)*
2. **Given** local SQLite, **Then** it serves as durable parse + offline cache + raw retention, authoritative for a set until it syncs. *(AR-3)*
3. **Given** a set already captured, **When** re-detected, **Then** it is not duplicated locally (deterministic session identity). *(AR-2 foundation)*
4. **Given** an interrupted or partial session (laptop sleep, agent crash, drive yanked mid-gig), **Then** "completed" is defined by an explicit completion signal — a partial capture is marked **incomplete** and is **not** synced as if it were the whole night; it either resumes or is flagged, never silently truncated. *(Boundary's hole #3, party 2026-07-20 — sharpens FR-1's "completed session")*

- [x] Task 2: Local SQLite store module (AC: #2, #3)
  - New `agent/src-tauri/src/store.rs`, registered as `pub mod store;` in `lib.rs`. Owns a single SQLite database file distinct from any Serato-owned database — suggested path `app.path().app_local_data_dir()?.join("local.sqlite")` (Tauri 2's per-machine, non-roaming data dir; mirror `settings.rs`'s `NoAppConfigDir`-style error variant, e.g. `StoreError::NoAppDataDir`, and its `create_dir_all` idiom before opening).
  - Schema (one table, created via `CREATE TABLE IF NOT EXISTS` on first open — no external migration tooling needed for a single-owner local file, unlike Supabase's migration-file convention):
    ```sql
    CREATE TABLE IF NOT EXISTS captured_sessions (
      id                INTEGER PRIMARY KEY AUTOINCREMENT,
      session_identity  TEXT NOT NULL UNIQUE,
      source            TEXT NOT NULL,        -- 'legacy' | 'serato4'
      status            TEXT NOT NULL,        -- 'watching' | 'captured' | 'incomplete'
      raw_ref           TEXT NOT NULL,        -- legacy: absolute .session path; serato4: "<db_path>#<serato_session_id>"
      started_at        INTEGER,              -- unix epoch seconds, first known play start_time
      ended_at          INTEGER,              -- unix epoch seconds, last known play start_time
      captured_at       INTEGER,              -- agent wall-clock time this row reached 'captured'
      plays_json        TEXT,                 -- serialized Vec<CapturedPlay>, NULL until captured
      derived_json       TEXT,                -- serialized CapturedDerived (stats + confidence), NULL until captured
      synced_at         INTEGER               -- NULL forever in this story; Story 3.2 owns setting it
    );
    ```
  - `session_identity` carries the `UNIQUE` constraint that *is* AC-3's dedup mechanism: upsert via `INSERT ... ON CONFLICT(session_identity) DO UPDATE SET ...` (SQLite's native upsert, available since 3.24 — `rusqlite` with the `bundled` feature already ships a current SQLite), never a check-then-insert race. A re-detected/re-parsed session updates the existing row's content columns in place — mirrors AD-4's "re-parse updates content, never re-partitions" philosophy applied locally, ahead of Story 3.2 applying the same philosophy to the cloud row.
  - Small public API, following this crate's error-enum idiom (`StoreError` with `Io`/`Sqlite`/`NoAppDataDir`/`Json` variants, `Display` + `std::error::Error`, no `anyhow`/`thiserror`): `open(app: &AppHandle) -> Result<Connection, StoreError>` (creates dir + file + schema); then plain functions taking `&Connection` (mirrors `joiner::serato4`'s `&Connection`-parameter style, not a wrapper struct) — `upsert_watching(...)`, `upsert_captured(...)`, `mark_incomplete(...)`, `get_by_identity(...)`, `status_of(...)`. Exact signatures are an implementation decision; keep them narrow and testable with an in-memory or temp-file `Connection`, matching every other SQLite-touching module in this crate.
  - Do **not** add a `sync_status`/queue-processing concern beyond the `synced_at` column existing as a nullable placeholder. Building the sync-queue is Story 3.2/3.3's job; this story only needs the column to exist so those stories don't need a schema migration to add it later (this local file has no additive-only migration discipline like Supabase — it's fine to evolve it directly in a later story, but reserving the column now costs nothing and documents intent).

- [x] Task 4: Session-identity + completion-signal design (AC: #3, #4) — read this before Task 5
  - **`session_identity` is this story's own local dedup key, computed per source, format-prefixed so the two sources' identity spaces can never collide in the same `UNIQUE` column:**
    - **Serato4**: `format!("serato4:{}", history_session.id)` — `history_session.id` is Serato's own auto-increment primary key for the session row (`parser::SessionSummary.id`), immutable once assigned and never derived from a file mtime/name/path — satisfies AD-16's "immutable start-anchor... never file mtime, path, or filename" directly, no computation needed.
    - **Legacy**: no `history_session`-equivalent table exists — the `.session` file itself is one session, but AD-16 explicitly forbids keying off the file's own mtime/path/name. Use the **first play's own identity** (AD-16's literal phrase: "its immutable start-anchor / first-play identity"): `format!("legacy:{:x}", hash(first_play.path, first_play.start_time))` where `first_play` is `plays[0]` after `parser::parse`'s existing start-time ordering (deterministic per Story 1.3's own guarantee) and `hash` is any stable, deterministic hash (e.g. a simple `DefaultHasher` over the tuple, or a small manual combine — no crypto requirement, this is a local dedup key, not a security boundary). If `plays` is empty (a session with zero plays — legitimate, see Story 1.3's `zero_oent_parses_to_empty_vec`), there is no session to capture at all; skip it rather than inventing an identity for nothing.
    - This is **not** the same computation Story 3.2 will use for the cloud `set_id = hash(dj_id, session_identity)` (AD-4/AD-16) — this story has no `dj_id` (no auth wiring in the agent yet, AR-10/Story 2.10 territory) and no cloud. It is a **local-only** dedup key satisfying this story's own AC-3. Story 3.2, when it lands, reads this row and computes its own cloud-facing hash from whatever intrinsic identity it has available (likely this same `session_identity` string, minus the format prefix, or the prefix carried through — that reconciliation is Story 3.2's decision, not this story's).
  - **Completion signal, per source (AC-4):**
    - **Serato4**: `history_session.end_time` transitioning from unset (`-1`, per Story 1.3b's confirmed real-data sentinel — **not** SQL `NULL`) to a real (non-negative) value is the completion signal. This directly closes the `deferred-work.md` entry *"`end_time: Some(-1)` sentinel inconsistency... becomes Story 2.8's concern once it consumes `SessionSummary` for real."* A session first appears via `watcher::check_for_new_sessions`'s watermark advance with `end_time` very likely still `-1` (the DJ is still playing) — this story must **not** capture it then. Track sessions seen-but-not-yet-complete (e.g. a small in-memory `Vec<i64>`/`HashSet<i64>` of pending Serato4 session ids, populated when `check_for_new_sessions` first sees them) and, on a cadence (reuse the existing `RECONNECT_POLL_INTERVAL` tick in `watch_loop`, no new timer), re-query `history_session` for just those specific ids (a small, bounded `WHERE id IN (...)` — you'll need a new small query in `parser::serato4`, e.g. `session_by_id(conn, id) -> Option<SessionSummary>`, or reuse `list_sessions_after` with `after_id = id - 1` and filter to the one row) to check whether `end_time` has since resolved. Once resolved, run Task 5's pipeline and drop the id from the pending set. Persist a `status = 'watching'` row (Task 2) as soon as a session is first seen, before completion — this is what makes the pending-check durable across an agent restart (reload pending ids from any `status = 'watching'` rows on `store::open`, rather than only tracking them in memory).
    - **Legacy**: no per-session end marker exists in this format at all — the current `notify` watch on `History/Sessions/` fires on file create/modify events but (per Story 2.6's own comment) does nothing with them yet. Define completion as a **quiet period**: no modify event observed for a given `.session` file for `LEGACY_QUIET_PERIOD_SEC` (new constant, `[ASSUMPTION]` — no prior story or research doc pins this number; a reasonable starting default is 15–20 minutes, long enough that a DJ's between-tracks silence or a bathroom break never falsely completes a set, short enough that a session completes within the same session as the gig for a same-morning dashboard view — flag this in Completion Notes for Arjun same as `confidence.rs`'s `LONG_GAP_THRESHOLD_SEC` was flagged). Track last-seen-modified time per watched `.session` file path (a small in-memory map, reloadable from `status = 'watching'` rows' `raw_ref` + filesystem `mtime` on restart) and check elapsed-since-last-event on each `RECONNECT_POLL_INTERVAL` tick, same cadence as the Serato4 pending-check above — no second timer.
    - **"Incomplete" (AC-4's explicit third state):** hook the *existing* disconnect transition already in `watch_loop` (the `connected` variable flipping to `Some(false)`, which currently only sets the tray to `DriveNotConnected`) — when this fires while one or more sessions for that path are `status = 'watching'` in the store, mark them `status = 'incomplete'` rather than leaving them ambiguously `'watching'` forever. On reconnect (`connected` flipping back to `Some(true)`), re-attempt the normal completion check for any `'incomplete'` rows on that path — if the completion signal now resolves (Serato4 `end_time` set; legacy quiet-period re-evaluated from the file's current mtime), promote straight to `'captured'` (AC-4's "it either resumes"); if the source is simply gone (file deleted, session id no longer present), leave it `'incomplete'` (AC-4's "or is flagged") — this story does not need a UI to surface incomplete sessions (no web/dashboard exists yet), only the data model distinction, so a future story can.

- [x] Task 5: Wire the full parse → join → embedded-tag-fallback → enrich → stat → confidence pipeline (AC: #1)
  - New `agent/src-tauri/src/capture.rs`, registered as `pub mod capture;` in `lib.rs`. One function per source, both converging on a shared "build `(Vec<CapturedPlay>, CapturedDerived)` from plays + a way to resolve library metadata" helper so the per-play assembly logic (embedded-tag fallback, `enrich_session`, stat calls, `confidence::classify`) is written once, not duplicated per source.
  - **Legacy path:** `parser::parse_session_file_partial(path)` (the tolerant entry point — a session captured at quiet-period completion is, by construction, no longer being appended to, but using the `_partial` variant costs nothing and is consistent with "never let a single malformed trailing record void an otherwise-good capture," matching this crate's existing tolerance philosophy) → for each `Play`, `joiner::legacy::LegacyLibrary::load(library_root)` (load once per capture, not per play — cache the loaded `LegacyLibrary` across the whole session's plays) → `joiner::legacy::join(&play, &library)` → `joiner::embedded_tags::fill_gaps(joined, play.path.as_deref())` → collect `(Play, JoinedMetadata)` pairs in order → `stats::enrich_session(&pairs)`.

    - **Close the deferred correlation-risk gap** (`deferred-work.md`: *"`enrich_session`'s pairing API rests on an implicit, untested cross-module invariant"* and *"Connection-sharing contract... has no integration test"*): both queries share the identical `ORDER BY start_time ASC, id ASC` clause over the same `WHERE session_id = ?1`, and `id` is a unique primary key — a fully-specified `ORDER BY` with a unique tiebreak produces one mathematically determined row order regardless of which columns were selected, so a positional zip of the two `Vec`s is provably safe *as long as the two `ORDER BY` clauses stay textually identical*. Add an integration test in `capture.rs` (or wherever the wiring lives) using an in-memory `master.sqlite` fixture with **two plays sharing the same `start_time`** (the exact case the doc comments warn about), asserting the zipped `(Play, JoinedMetadata)` pairs correlate correctly (e.g. a distinguishing field like `title`/`bpm` set per-row so a misalignment would be observable, not just "both vecs have the same length"). This is the "explicit alignment check" `deferred-work.md` asks for — do not change `read_session`'s or `join_session`'s signatures to add a shared correlation id; that would touch two other stories' shipped, tested code for a risk this test closes just as well.
    - Build `(Play, JoinedMetadata)` pairs by zipping the two `Vec`s positionally (now test-backed, per above) → `stats::enrich_session(&pairs)`.
  - **Both paths converge:** `EnrichedPlay`s (with paired `in_library`, per Task 3) → `stats::most_played_tracks`, `stats::most_played_artists`, `stats::genre_breakdown`, `stats::bpm_distribution`, `stats::set_length_sec`, `stats::track_count`, `stats::camelot::mixing_stats`, `stats::energy_arc` (all pure functions over `&[EnrichedPlay]`, call each once) → `confidence::classify(&enriched_plays)` → assemble `CapturedDerived` → `store::upsert_captured(...)`.
  - **Raw retention (AR-3) is source-dependent, not a single mechanism:**
    - Legacy: the `.session` file itself is never moved/deleted by `parser::parse_session_file`/`parse_session_file_partial` (Story 1.3's read-only guarantee) — "raw retention" here means the store's `raw_ref` column pointing at that path is sufficient; do not copy the file's bytes into SQLite.
    - Serato4: per Story 1.3b's own Dev Notes, *"There is no separate 'raw file' for this format to retain — the live `master.sqlite`, owned by Serato, already is the durable source"* — `raw_ref` recording `"<db_path>#<serato_session_id>"` is sufficient; a future backfill (AR-7) re-reads directly from `master.sqlite`, no duplication needed.

## Dev Notes

- **What actually exists today (read before Task 1) — this is genuinely new-code territory, not an extension:**
  - Stories 1.3, 1.3b, 1.4, 1.5, 1.6, 1.7, 1.8 are all `done`, fully unit-tested, and have **zero production callers**. This story is the first to call `parser::parse_session_file_partial`/`parser::serato4::read_session`, `joiner::legacy::{LegacyLibrary::load, join}`/`joiner::serato4::join_session`, `joiner::embedded_tags::fill_gaps`, `stats::enrich_session` + its stat functions, and `confidence::classify` in a real pipeline.
  - No local SQLite store exists. `rusqlite` is currently used only for **read-only** access to Serato's own databases (`joiner::serato4::open_read_only`) — this story is the first to open a SQLite connection the agent itself owns and writes to.
  - `agent/src-tauri/src/` today: `lib.rs, confidence.rs, fs_scope.rs, genre.rs, tray.rs, main.rs, settings.rs, joiner/{mod,serato4,legacy,embedded_tags}.rs, parser/{mod,session,serato4}.rs, stats/{mod,camelot}.rs, watcher/{mod,detect}.rs` — no `store.rs`, no `capture.rs` yet.

- **Scope boundaries — do not build these here:**
  - Cloud sync (`PUT /sets/:set_id`), the sync-queue, `dj_id`-namespaced hashing → Story 3.2/3.3. This story's local `session_identity` is explicitly **not** the cloud `set_id` computation (see Task 4).
  - Agent auth/token storage → Story 2.10. No `dj_id` exists in the agent yet; the local store has no per-DJ concept (there is only ever one DJ per agent install).
  - A UI/dashboard to surface `incomplete` sessions → no web/dashboard exists yet (Epic 3). This story's job ends at the data model correctly distinguishing the states.
  - Segment detection (AD-17/Epic 5), Layer 2 enrichment, visibility tiers — all cloud-side overlays (AD-6), irrelevant to local capture.
  - The `TrackIdentity` `(title, artist)` collision for pathless Serato4 plays (`deferred-work.md`, Story 1.7) and the `in_library` "guessed `true`" flag for Serato4 (`deferred-work.md`, Story 1.4) are pre-existing, known, accepted limitations this story does not fix — it persists whatever `stats`/`joiner` already produce, faithfully.

- **Why per-source completion signals, not one shared mechanism:** the two formats have genuinely different available signals (Serato4: an explicit DB column that flips; legacy: no equivalent field exists anywhere in the confirmed schema, per Story 1.2's findings). Forcing one mechanism onto both would mean inventing a fake signal for whichever format doesn't naturally have it — exactly the kind of guess AD-11 forbids. This mirrors Story 2.6's own precedent of two genuinely different detection mechanisms (OS-default paths, install-generation classification) rather than one unified check.

- **Error-handling idiom (repo-wide convention, mirror it):** small enum, `Io`/format-specific variants, `Display` + `std::error::Error`, no `anyhow`/`thiserror` — see `SettingsError`, `ParseError`, `JoinError`, `ScopeError`, `OpenError`. `StoreError` (Task 2) follows the same shape.

- **Testing conventions:** temp-dir/temp-file fixtures with unique-per-test naming + `Drop` cleanup (see `settings.rs`'s `TempSettingsFile`, `watcher/detect.rs`'s `TempDir`) for `store.rs`; in-memory `rusqlite::Connection` fixtures (see `joiner/serato4.rs`'s `in_memory_history()`) for the Serato4 capture path; synthetic byte-fixture builders (see `parser/session.rs`'s `oent`/`play_record` helpers) for the legacy capture path. Never commit real Serato data as a fixture — golden fixtures are Story 1.9's job, and every real-data spot check in this project's history has been a throwaway, uncommitted script.

- **Architecture citations:** AR-3 ("Two stores, one owner per class" — local SQLite is durable parse + offline cache + raw retention, authoritative for a set only until synced) is this story's primary governing invariant. AD-16 governs `session_identity`'s derivation rule (immutable start-anchor/first-play identity, never mtime/path/filename) and previews the AD-4 dedup philosophy (re-parse updates content, never duplicates) this story applies locally ahead of Story 3.2 applying it to the cloud row. AD-13 (format-drift resilience, backfill from raw retention) is the reason raw retention (Task 5) matters at all — a future parser fix needs to re-derive from what this story retains.

- [x] [Review][Patch] `upsert_watching`'s `ON CONFLICT ... DO UPDATE SET` never assigns `status` — resuming a disconnected session leaves its DB row stuck at `'incomplete'` forever, breaking AC-4's resume guarantee.
