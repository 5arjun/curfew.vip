# Story 2.10: Agent secure token storage

Status: done

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As a DJ,
I want the agent to authenticate to the cloud and persist its refresh token securely,
so that my sets sync under my account without re-login and without exposing tokens.

## Acceptance Criteria

1. **Given** the agent links to my account, **Then** it obtains a Supabase JWT + refresh token and persists the refresh token via Tauri secure storage (not browser storage). *(AR-10)*
2. **Given** an expired JWT, **When** the agent syncs, **Then** it refreshes transparently. *(AR-10)*
3. **Given** the stored token, **Then** it is scoped to my `dj` account so captured sets sync under the correct `dj_id`. *(AR-10, AR-4)*

### Resolved before this story was written (read first — binding decisions, not open questions)

The epic text only says "the agent links to my account" — neither the epic nor ARCHITECTURE-SPINE.md/SOLUTION-DESIGN.md specify the actual pairing mechanism, and no pairing/deep-link/device-code code exists anywhere in the repo (confirmed by repo-wide grep). This is a genuine architecture gap the epics never closed. **Arjun ruled on it during story creation (2026-07-30):**

- **Mechanism: deep-link callback.** The agent opens the DJ's system browser to a `web/` page. The DJ is already authenticated there (Stories 2.3a/2.3b/2.3d) or logs in on the spot via the existing `/login` flow. Once authenticated, that page reads the **already-issued** Supabase session (access token + refresh token) straight out of the browser client and hands it to the agent via a **custom URI scheme redirect** (`curfew-agent://link?access_token=...&refresh_token=...`), which Tauri's official deep-link plugin captures.
- **Why this and not a pairing code / device-code flow:** both alternatives need a new backend surface (a `pairing_codes` table + an endpoint to mint/exchange codes, or a device-code polling endpoint) — AD-8 ("all cloud mutation goes through Supabase + RLS... no custom mutation server at v1") and AD-14 ("no premature microservices... future service seams are named, not built") both cut against inventing one for this. The deep-link approach needs **zero new backend surface**: it only ever moves tokens Supabase already issued to an already-authenticated browser session, client-side, once.
- **This is the story's single biggest implementation risk area** — get the deep-link registration and single-instance handling right (Task 3) before anything else, per the gotcha called out there.

A missing refresh token at startup (never linked, or cleared) is not an error — leave the in-memory state `None` and let Task 3/6's "Link Account" flow populate it later.

### Review Findings

**Code review (bmad-code-review, 3 parallel layers — Blind Hunter, Edge Case Hunter, Acceptance Auditor), 2026-07-30.**

- [x] [Review][Patch] Deep-link handoff has no CSRF/nonce binding — `handle_link_url` (`agent/src-tauri/src/lib.rs:125-144`) accepts and persists whatever `access_token`/`refresh_token` arrive on any `curfew-agent://link` URL unconditionally, with no shared secret tying the request to the specific "Link Account" click that opened the browser. A malicious page that gets the DJ to trigger the same URL shape (auto-redirect, hidden iframe, crafted link) could silently repoint the agent to an attacker's Supabase account. **Decision resolved by Arjun (2026-07-30): add the nonce round-trip now.** Fix: agent generates a one-time nonce when opening the browser via the tray "Link Account" item, passes it as a query param to `/link-agent`, the web page echoes it back into the `curfew-agent://link` redirect, and the agent validates + single-use-consumes it (reject/no-op on mismatch or replay). No new backend surface needed, so this doesn't violate AD-8/AD-14. `decode_jwt_claims` (`agent/src-tauri/src/auth/client.rs:68-74`) never verifies the JWT signature either — already disclosed/justified in the code's own doc comment (Supabase verifies server-side; local decode is display-only for the tray label), noted here only as supporting color, not an independent defect to fix.

- [x] [Review][Patch] Cold-start deep-link check can crash the entire agent on any plugin error [agent/src-tauri/src/lib.rs:373] — `if let Some(urls) = app.deep_link().get_current()? { ... }` uses `?` inside `.setup()`, so any `Err` (not just "no pending URL") propagates out and fails the whole app (the outer `.run(...).expect(...)` then panics). Inconsistent with every other error path in this same function — the home-dir resolution a few lines above was deliberately changed away from exactly this `?`-propagation pattern, with a comment explaining why. Fix: handle the `Result` gracefully (e.g. `if let Ok(Some(urls)) = app.deep_link().get_current()`) instead of propagating.

- [x] [Review][Patch] `Cargo.lock` resolved a security-regressed `reqwest`/`rustls-platform-verifier` pair [agent/src-tauri/Cargo.lock] — the diff shows `reqwest` 0.13.4 → 0.13.1 and `rustls-platform-verifier` 0.7.0 → 0.6.2. Verified via reqwest's own changelog: 0.13.4 contains a real security fix (strips sensitive headers, e.g. the `apikey` header this client sends on every refresh call, on cross-scheme redirects) that 0.13.1 lacks. Fix: `cargo update -p reqwest --precise 0.13.4` (or equivalent) to restore the patched version; re-verify the lockfile resolves cleanly.

- [x] [Review][Patch] Startup eager-refresh runs a blocking HTTP client synchronously inside `.setup()` [agent/src-tauri/src/lib.rs:388-393, agent/src-tauri/src/auth/client.rs:114-119] — this call path runs on literally every agent restart once linked (access tokens are memory-only, never persisted, so a refresh is attempted every boot). Three compounding issues: (a) unverified risk of a "cannot start a runtime from within a runtime" panic if Tauri's setup closure executes inside an already-entered async context (`reqwest::blocking::Client`'s known footgun) — the one manual walkthrough doesn't clearly confirm this exact call site (cold boot with an already-expired token) was exercised; (b) no `.timeout()`/`.connect_timeout()` configured, so an unreachable/slow host can hang agent startup indefinitely; (c) failure is completely silent (`let _ =`), not even logged in debug builds, unlike every other auth error path in this file. Fix: move the call onto a spawned background thread (sidesteps the runtime-nesting risk entirely) and add a timeout + at least debug-only logging.

- [x] [Review][Patch] Tray link status never updates after a live link event [agent/src-tauri/src/lib.rs:125-144, 234-240, 395-405] — "Linked as `<dj_id>`"/"Not linked" is computed exactly once at startup; `handle_link_url` never touches `link_status_item`. The realistic linking path (agent already running, DJ clicks "Link Account" — the story's own documented common case) leaves the tray showing stale status indefinitely even though linking succeeded or failed internally. This is the one UI surface Task 6 asks for, and it also covers the related "keychain-save failure during linking gives no release-build signal" case (same root cause: nothing in `handle_link_url` reaches the tray text on either outcome). Fix: thread `link_status_item` (or an updater closure) into `AuthState`/`handle_link_url` so a live link event refreshes the tray text on both success and failure.
