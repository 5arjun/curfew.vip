## Scoping the email-provider work

Recommendation: **`bmad-correct-course`, not `bmad-create-story`.**

Reasoning: `bmad-create-story` drafts a dev-ready story file from a description that already exists in `epics.md` (that's exactly what happened for 2.3a and 2.3b — both were already stubbed out in the Epic 2 story list before context-engineering). The email-sending provider has **no existing entry anywhere in epics.md** — it's net-new scope discovered mid-epic, not a story waiting to be detailed. `bmad-correct-course` is the tool built for exactly this: a significant gap found during sprint execution that needs the epic/story backlog itself updated (new story inserted, possibly a one-line architecture-spine note added since production SMTP config is an AD-10/Supabase-Auth-adjacent decision) before a story file gets written against it.

Likely shape once correct-course runs: a new story in Epic 2 (natural fit — it directly unblocks Story 2.3a's confirmation email in production, and Epic 2 already owns the Supabase Auth configuration surface), scoped to (a) standing up a Resend-or-similar account + verified sending domain (manual, Arjun's call, same pattern as PROVISIONING.md), and (b) the coding half: uncommenting/filling `[auth.email.smtp]` in `config.toml` with env-var-sourced secrets, confirming it applies to both local and the eventual cloud project, and documenting the runbook the same way Story 2.1 documented Supabase provisioning.

Ready to run `bmad-correct-course` for this now if you want to proceed.
