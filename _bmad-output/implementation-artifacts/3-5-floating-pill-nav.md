# Story 3.5: Floating pill nav

Status: done

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As a DJ,
I want the signature floating pill nav present on every authenticated screen,
so that navigation is consistent, glanceable, and keyboard-operable.

## Acceptance Criteria

1. **Given** any logged-in screen, **Then** the bottom-center nav dock (opaque `--color-surface-void`, animated conic-gradient shine border, `--radius-2xl` corners) is present. *(UX-DR2 — originally specified as a glassy pill: backdrop-blur over `surface-container` @90%, static hairline border, full pill radius. **Corrected, Arjun's ruling, code review 2026-08-05:** mid-session verbal direction during this story's own dev-story session (see Dev Agent Record Change Log) moved the nav through several "dock revisions" — opaque void fill replaced the translucent glass (an opaque fill has nothing to blur), a spinning conic-gradient shine replaced the static hairline border, and the shape squared off onto `--radius-2xl` (`--radius-full` stays reserved for the avatar/status dots per `2-2-obsidian-design-token-system-web-shell.md`). This AC text was never synced to that decision until now; the shipped dock treatment is the operative spec.)*
2. **Given** the nav, **Then** the active item is styled with `--color-nav-chip-active` (a near-invisible white raised chip) and `--color-on-surface` icon/label. *(UX-DR2 — epics.md's literal wording, "solid lavender," is stale phrasing from the original Electric Lavender palette, carried through the Ice-Cyan revision and superseded again by the 2026-07-28 "Ember" revision, and now superseded a third time. The wording was first corrected to `--color-primary` (Ember rose `#e98aa2`) per Story 2.4's precedent — **then corrected again, Arjun's ruling, code review 2026-08-05:** a later mid-session "dock revision" (see Dev Agent Record Change Log) deliberately moved off the pink-glow/`--color-primary` fill to a neutral raised chip, reasoning that a filled pastel block "read as a consumer default" and that selection should be carried by fill-weight glyph + label reveal, not a color tint. This AC text was never synced to that decision until now; the shipped neutral-chip treatment is the operative spec. **Also corrected, Arjun's ruling this session [2026-08-01]:** epics.md's AC-2 additionally specifies "the menu trigger opens an upward popover... for secondary items" — deliberately not built; see Dev Notes "Nav structure decision" §2 for why a menu trigger with nothing behind it was cut rather than shipped empty.)*
3. **Given** keyboard-only use, **Then** every nav item is fully operable. *(UX-DR2, UX-DR21)*
4. **Given** mobile, **Then** the nav stays bottom-anchored. *(UX-DR22)*

### Scope boundaries (binding — read before writing code)

- **In scope:** the `FloatingNav` component itself — four primary direct links (Dashboard, Style Evolution, Library Utilization, **Profile/Settings**) that directly and fully represent the nav (no hidden/overflow menu), active-item styling, full keyboard/hover operability, mobile bottom-anchoring; introducing Tailwind CSS + shadcn/ui to `web/` (Arjun's ruling, this story's creation session — see Dev Notes); introducing `@phosphor-icons/react`; a new `(authenticated)` route group + `layout.tsx` that mounts the nav; minimal temporary stub pages at the four destination routes purely so the nav can be manually verified end-to-end in a real browser (see "Temporary stub pages," Task 5).
- **In scope, but an *interim* treatment — Profile/Settings.** Added mid-session at Arjun's request. DESIGN.md/Story 3.10 specify the *final* form as a circular Avatar image with no icon at all — but no photo/avatar-image infrastructure exists yet (that's Story 3.10's job, alongside the real Profile/Settings page content), and per this story's own "represent it directly, don't hide it" logic (see "Nav structure decision" §1) it shouldn't wait either. **This story ships a fourth icon-based link** (`UserCircle`, same visual treatment as the other three — see Task 3.5/3.6), with a stub destination page (Task 5.2), exactly like the other three. **Story 3.10 replaces the icon with a real circular avatar photo and builds the real destination** — it does not need to restructure the nav, just swap one item's rendering.
- **Out of scope — do not build:**
  - **A menu-trigger/hamburger button and its popover.** epics.md's AC-2 names one ("the menu trigger opens an upward popover... for secondary items"), and DESIGN.md's prose does too — but as established with Arjun earlier in this story's creation session, zero secondary items exist anywhere in the confirmed product scope today. Arjun's follow-up ruling: a hamburger button that opens on nothing is worse than not having one — showing several direct icons *and* a separate button that might reveal more is confusing, not glanceable. **Cut the trigger entirely; the direct links are the whole nav.** If a real secondary destination is ever added to the product (a later epic), reintroduce the trigger in whatever story adds that destination — don't pre-build the mechanism speculatively again.
  - **The real Avatar image.** See the "interim treatment" note above — this story ships a generic icon standing in for the avatar, not photo-based rendering, OAuth-picture lookup, or upload handling. That's Story 3.10's job in full.
  - **A "Sets" nav item and a raised center "+" action button.** Four of the five Stitch mocks (`curfew_dashboard_sticky_nav`, `curfew_style_evolution_sticky_nav`, `curfew_library_utilization_sticky_nav`, `curfew_set_detail_sticky_nav`) render exactly this — but neither a "Sets" page nor a "+" action exists anywhere in EXPERIENCE.md's Information Architecture table or Key Flows. This is a real, confirmed mock/spec conflict (Arjun's ruling, this story's creation session): **build the written spec, not the dominant mock.** See Dev Notes "Nav structure decision" for the full reasoning — do not rediscover this as an open question.
  - **Any real Dashboard/Style Evolution/Library Utilization/Profile-Settings page content.** Those are Story 3.6, Epic 4, and Story 3.10's job respectively. This story's stub pages (Task 5) are placeholders only, explicitly superseded when those stories land.
  - **Any Landing-page nav.** The logged-out `curfew_landing_page_sticky_nav`/`curfew_login_sticky_nav` mocks show a different nav (Login/Features/menu-popover) for the pre-auth surface — that's Epic 6 territory (Story 6.1/6.4), not this story.

### Tailwind/shadcn integration risk (read before Task 1/2)

This repo's **one enforced anti-drift invariant** is `no-hardcoded-colors.test.ts` (`web/app/no-hardcoded-colors.test.ts`) — it scans every `.ts`/`.tsx`/`.css` file under `web/app/` (excluding `tokens.css`, `fonts.ts`, `*.test.ts`) for hex/rgb/hsl/named-color literals, and every prior web story has built cleanly against it. Introducing Tailwind + shadcn is the single biggest risk to that invariant this repo has ever taken on, because both tools' default setup flows assume you'll define fresh color values in a theme/config file — **do not do that here**. Every new color-bearing token (Tailwind's `@theme` block, shadcn's aliased variable names) must be a `var()` reference back into the *existing* `tokens.css` custom properties, never a new hex literal. Run the guard early and often (Tasks 1.5, 2.5, 7.2) rather than discovering a violation at the end.
