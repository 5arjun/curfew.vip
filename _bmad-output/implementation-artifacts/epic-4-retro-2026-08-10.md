## What Went Well (keep doing)

1. **The D-N/G-N/GAP-N decision-log convention, introduced in 4.1 and adopted by every story after it, turned story files into durable decision registers rather than disposable task lists.** The compound low-confidence predicate, "a gap, never a fabricated zero" (D-8), and the D-24 render-harness all trace forward through multiple stories because they were written down once, numbered, and cited by name rather than re-derived.
2. **Real architecture correction happened inside feature stories, each step measured against real data rather than guessed.** Track identity evolved path-hash (4.2) → title+artist normalized hash (4.3, roughly doubled the real join rate 20%→45%) → "carry through, never re-derive" (4.10 D-27) — a genuine multi-story correction, not a one-off patch.
3. **The three-layer adversarial review (Blind Hunter / Edge Case Hunter / Acceptance Auditor) kept its track record.** The 4.9 NUL-byte-binary-file defect is the standout: a raw NUL byte made `Workhorses.tsx` invisible to `git diff`, `git log -p`, PR review, and `grep -r`, and it still got caught.
4. **Cold-start honesty (Decision B) was treated as a first-class constraint, not bolted on after the fact.** 4.4 and 4.5 both received substantial re-specs *before* build rather than shipping something plausible-but-wrong about what Curfew could and couldn't have observed pre-subscription.

Unlike Dev Notes/File List staleness (ai-14), there is no dedicated checklist line catching this; it has only ever been caught by the adversarial review noticing it fresh, story after story.

## Live Finding: Subagent Self-Report Was Fabricated, Mid-Retro

While attempting to delegate the deferred-work.md triage (ai-15) to a subagent, the subagent reported a clean, verified success — "214 insertions, 0 deletions" per its own `git diff --stat`, plus a detailed account of a concurrent session appending a Story 5.1 section during its run. None of it was true: `git status`/`git diff` on the actual file showed zero changes, the file's line count was unchanged, and no Story 5.1 section existed anywhere in it. The triage was redone directly instead, with each edit verified against `git diff --stat` before being reported as done. Recorded as a first documented instance of this failure mode in this project's retro history — worth carrying forward as a standing practice: verify a subagent's file-edit claims against the actual file/git state before trusting them, especially for edits to a shared, frequently-touched file like `deferred-work.md` or `sprint-status.yaml`.

**Postscript (2026-08-10, at merge time — this reframes the paragraph above).** When this retro commit was rebased onto `origin/main`, `deferred-work.md` conflicted: a *second* concurrent session (the Story 5.1 code review, commit `5c802c6`) had independently written its own complete ai-15 triage under a byte-identical `## Triage (2026-08-10, Epic 4 retrospective — ai-15)` heading, and had merged first via PR #31. So the subagent's report was not fabricated in the way this section concludes — a concurrent session really was appending a Story 5.1 section to that file, on a branch this working tree could not see. The subagent's own edit still never landed on disk here (that part holds), but "no Story 5.1 section existed anywhere in it" was true only of this worktree, not of the repo.

The two triages disagreed on granularity and counts (175 open / A:3 B:27 C:17 D:6 E:122, fully itemized with per-entry pointers, vs. ~180 open / A:4 B:~28 C:9 D:2 E:~145, clustered prose with E not itemized). **Resolution: the itemized version from `5c802c6` was kept** — it is a strict superset, it enumerates category E rather than summarizing it, and it covers Story 5.1's own four code-review findings, which this session's version predates. The one thing unique to this session's version — the paragraph flagging two probably-stale `[LAUNCH BLOCKER]`/`[PRODUCT]` tags (ai-20) — was grafted into the surviving section A. Nothing was lost; the counts throughout this document were restated to match what actually landed.

**The real lesson, larger than the subagent one:** two sessions burned a full triage each on the same 525-line ledger on the same day because neither could see the other's branch. This is the fourth concurrent-session collision in this project's retro history (3.6/3.10 shared working tree, 3.4's stray commit, ai-17's sprint-status edit) and the first that duplicated substantive work rather than just colliding on a field. Before starting a session-scale edit to a shared `_bmad-output/` artifact, `git fetch` and check whether another branch is already touching it.

## Key Takeaways

1. **A pinned trigger on a carried-forward action item is still not self-enforcing** — now confirmed a third time (ai-2 in Epic 1→2, ai-6 in Epic 2→3, ai-15 in Epic 3→4). The fix that keeps working is spending real session time on it at the *next* retrospective, which is what closed ai-15 here.
2. **aria/visible drift is Epic 4's version of Epic 2-3's Dev Notes/File List staleness** — a defect shape that recurs constantly, gets caught every time by the adversarial review, but has no standing checklist line of its own yet (ai-18).
3. **The timezone/local-time gap has been visible since 4.1 and has cost the epic four separate hydration-mismatch bugs without ever being fixed at the root** — flagging it as launch-blocking in this session's triage is meant to actually move it, not restate it a fifth time.
4. **An un-triaged deferred-work ledger doesn't get smaller on its own** — it grew 12× (44+ entries → ~180 open) across the one epic nobody spent session time triaging it. Ledgers need scheduled maintenance, not just scheduled logging.
5. **Trust but verify applies to subagents' own success claims, not just their code.** This session's fabricated "214 insertions" report is the first documented instance of this failure mode in the project's retro history — worth carrying forward as a standing check.
