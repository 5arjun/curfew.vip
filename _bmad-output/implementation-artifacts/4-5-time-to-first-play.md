# Story 4.5: Time-to-first-play

Status: done

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As a DJ,
I want to see the elapsed time between adding a track and first playing it,
so that I understand how long tracks sit before they debut.

## Context & Authority

**The re-spec (binding, epics.md, 2026-08-07 party mode + Arjun).** As originally worded, "first play" read as a track's literal first-ever play. But Decision A's go-forward-only capture means Curfew only ever *observes* plays after it starts watching a DJ's library — for a veteran DJ's back catalogue (added years ago, played constantly pre-Curfew), the first play Curfew sees is not the track's true first play. Computing elapsed time against the real Serato add-date would read as "this track sat unplayed for three years" for a track that's been in steady rotation the whole time — the "first-play-garbage" failure Decision B flags for this story. **Fix: scope the metric's entire population to tracks whose add event Curfew itself observed go-forward.** Tracks outside that population are excluded outright, not marked "Unknown" — "Unknown" implies missing data for a track this feature covers; a pre-observation track isn't in this feature's domain at all.

**Population-boundary resolution (this session, Arjun — the epics.md text says "subscription start"; resolved to an implementable proxy).** Epic 7 (Stripe billing) is entirely `backlog` — there is no persisted subscription-start timestamp anywhere in the schema today. `djs` carries only `created_at` (account creation); the future AD-19 billing columns (`stripe_customer_id`, `stripe_subscription_id`, `subscription_status`, `current_period_end`) are current-state only, with no start-date column, even once built. **Ruling: use `library_track_events` membership itself as the population boundary — no new column, no Epic 7 dependency.** This works by construction, not by approximation: Story 4.2's D-1 baseline-then-diff design means that table *only ever* contains tracks whose add was observed **after** the agent's local first-run baseline (or, per 4.2's Completion Notes finding 1, after a late-mounted volume's own baseline catch-up) — a track present pre-baseline is silently absorbed into the baseline and never emitted as an add-event at all. So **every *dated* row already in `library_track_events` is, by construction, a go-forward add** — the exact population this story's re-spec asks for. This is the identical reasoning 4.2/4.3 already lean on for their own "since joining" framing; 4.5 does not need a second, stricter boundary layered on top of the one that already exists. **Consequence for the ACs below:** AC-1/AC-2's "on or after subscription start" is satisfied by reading `library_track_events` as-is — no additional filter against a subscription-start date needs to be written. Do not add a second population filter keyed off `djs.created_at` or a future billing column; it would be redundant, because every event already satisfies `added_at ≥ baseline`, and an account created before the agent's first run makes such a filter a pure no-op rather than a correction. *(Corrected 2026-08-07 by code review: this paragraph originally argued a `djs.created_at` filter would "incorrectly narrow" the population in that case. That is backwards — when `created_at < baseline` the filter narrows nothing at all; narrowing is only possible in the opposite case, `created_at > baseline`. The ruling stands; the reasoning for it did not.)*

**Two limits on the "by construction" guarantee (code review 2026-08-07 — the guarantee is real but narrower than first stated).**

1. **It covers dated rows only.** The agent's baseline partition is `match (added_at, baseline_at) { (Some(added), Some(baseline)) => *added < baseline, _ => false }` (`agent/src-tauri/src/capture.rs`) — the `_ => false` arm sends every track with no resolvable `tadd`/`uadd` to the emitted partition, deliberately (Story 4.2: "suppressing it would hide the very count D-10 exists to disclose"). So an **undated** row may predate observation by years. **Ruled 2026-08-07 (Arjun): AC-5 governs this subset** — undated tracks stay excluded from the math and disclosed as a count. AC-2's "never rendered as Unknown" is therefore scoped to tracks that never enter `library_track_events` at all, not to the undated rows inside it.
2. **A stale identity stratum may exist in the cloud table.** Story 4.3's Decision E-2 retired the path-hash `track_id` for a title+artist hash and handled the cutover by re-baselining the local store, explicitly leaving old cloud rows as "inert, unqueried leftovers — harmless, not cleaned up" (`4-3-...md:116`). **That ruling was made against a windowed metric** (4.3's meter looks back 60/30/14 days, so orphans fall outside it). This story is the first *lifetime-scope* consumer: an orphan row is dated, survives the null filter, can never join a post-cutover play, and therefore becomes a permanent `never-played` entry inflating both the visible count and the population gate. **Ruled 2026-08-07 (Arjun): clean it up before Story 4.6 — then CLOSED the same day as unnecessary.** Measured against production: `library_track_events` has 0 rows and no agent has ever synced, so the stratum does not exist. The reasoning above still stands as a real property of the design; it simply has no blast radius yet. See Completion Notes.

**Copy rule (binding, from Decision B, reused verbatim from 4.2/4.3).** Never surface elapsed subscription/observation time as *cost* (no "since you joined," no "in your N months"). Frame the record as the DJ's own ("your library," "tracks we've been watching"), never a receipt.

**No UX-DR wireframe exists for this specific component.** epics.md's Epic 4 FR-coverage line (`epics.md:202`) cites UX-DR6 (trend chart), UX-DR11 (progress pips), UX-DR12 (aging-shelf list) for FR-9–13 collectively, but none is a distribution/median display — that shape doesn't match this metric's shape (this is a per-track duration statistic, not a month-bucketed trend or a live percentage). `EXPERIENCE.md`'s Library Utilization row (line 25) names "time-to-first-play" as a feature but has no Components-table row for it yet. Building this component's visual form is therefore a **design call for the dev agent**, not a spec gap to escalate — same precedent as Story 4.3 Task 4 ("epics.md does not cite a UX-DR19 state for this specific meter, so this is a design call"). Recommended shape below (Dev Notes) is a suggestion, not a mandate.

## Acceptance Criteria

1. **Given** a track whose add event exists in `library_track_events` (per the population-boundary resolution above) and then first played, **Then** time-to-first-play = (first-play timestamp − add timestamp) is computed and displayed. *(FR-13; population scoped per the re-spec above)*
2. **Given** a track added **before** Curfew's go-forward observation began (i.e. absorbed into the local baseline, never present in `library_track_events`), **Then** it is excluded from this metric's population entirely — never computed, never counted toward the aggregate, and never rendered as "Unknown" (which would wrongly imply it belongs here but is missing a value). *(Decision B — a population boundary, not a data gap)*
3. **Given** a qualifying track never played, **Then** it is represented distinctly (not counted as zero, not silently omitted from any qualifying-population count the UI states).
4. **Given** the metric across qualifying tracks, **Then** an aggregate view (e.g. distribution/median) is shown, **and** a DJ with too few qualifying tracks sees the positive-framed insufficient-history state rather than a distribution drawn from a handful of points. *(UX-DR19)*
5. **Given** a qualifying track missing both `tadd` and `uadd` (~6% of tracks, per Architecture Spine Open Questions #2), **Then** time-to-first-play renders as "Unknown" (per FR-2's Unknown convention) and is excluded from the aggregate view — never computed against a missing timestamp. *(Architecture Spine OQ#2 graceful-fallback requirement; SM-C1)*
6. **Given** the `/library-utilization` route, **Then** the metric renders there, alongside the Story 4.3 conversion-rate meter — not on `/style-evolution`. *(epics.md §4.4 grouping, matching 4.3 AC-5's precedent)*

- 2026-08-07 — **Second review round (party mode: Mary, Paige, John, Sally, Winston, Amelia; Boundary walked on). Four findings decided and fixed.**
  - **Finding 1 — `played-before-add` was counted and then never read.** These tracks passed the population gate, contributed to neither the average nor `neverPlayedCount`, and were named nowhere in the UI: 20 tracks with 6 debuts and 14 of these reported on 6 and mentioned nothing. Worse, with `neverPlayedCount === 0` the summary fell through to *"No tracks have debuted yet."* about tracks the DJ demonstrably played — the exact false claim the `played-before-add` state was invented to prevent, one branch over. Mary's point on the evidence: the fixture's 4 is unrepresentative of the *mechanism* (`uadd` resetting on a re-add from a new drive or restored backup produces a batch, not strays). Winston's ruling on scope: this is AC-5's disclosure requirement unfinished, not new scope.
  - **Finding 3 — future-dated adds reconciled to nothing.** `continue` with no counter: not in `entries`, not `noAddDateCount`, not never-played, not played-before-add. Boundary's merge, adopted: findings 1 and 3 are the same sentence to a DJ ("the add date doesn't survive contact with the play history or the clock"), so they share **one** disclosure clause — while staying **two** model fields, because they are two facts. Deliberately not folded into `noAddDateCount`, which would be false: these tracks have a date.
  - **Finding 2 — the debut floor was misdiagnosed, and the fix is a hedge rather than a higher gate.** Bootstrap over the fixture's 233 real debuts (3000 resamples per size) put the sample mean's relative error at **99% typical / 240% p90 at n=5** — the shipped gate shows an average typically wrong by a factor of two — falling only to 40% at n=30 and 27% at n=50. No threshold makes a single point estimate honest at a sample size a real DJ reaches soon, and switching back to the median does not rescue it (the median is 51 minutes, so an hour of wobble is a 100% relative error; relative error is the wrong yardstick for a tiny number). Raising `MIN_TIME_TO_FIRST_PLAY_DEBUTS` was **rejected** — Sally's objection carried it: hiding the module from every DJ for months to protect a statistic fights the exact reason the mean was chosen. Instead the gate stays at 5 and the average carries the **same "early read" hedge the conversion meter 200px up the page already uses** below its own confidence floor (`TIME_TO_FIRST_PLAY_EARLY_READ_DEBUTS = 30`, with the measurement table written into the constant's doc comment at Winston's insistence). Sally's condition, accepted: the hedge lives in `timeToFirstPlaySummary` — the one generator — not only in the component, because a hedge a sighted user sees and a screen-reader user does not would be this module's *third* aria/visible drift.
  - **Finding 6 — the docstring contradicted its own signature.** `buildTimeToFirstPlay` claimed to take no `nowMs` directly above the parameter list that takes one; File List said `neverPlayedMedianAgeMs`/`median` where the code says `neverPlayedAverageAgeMs`/`mean`. Both corrected.
  - **Effect on the committed fixture:** the approved readout is **unchanged** ("233 tracks have debuted, an average of 2 weeks after being added — 286 others haven't been played yet"; 233 debuts is well clear of the hedge). One new page-level line appears where the disclosure was previously `null`: *"4 tracks have add dates Curfew can't reconcile — not counted here."*
