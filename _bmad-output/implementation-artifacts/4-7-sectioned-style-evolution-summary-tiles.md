# Story 4.7: Sectioned Style Evolution + summary tiles

Status: review

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As a DJ,
I want the Style Evolution page to show my tempo, genre, and key trends all at once with a summary row above them,
so that I can read my whole evolution in one glance instead of clicking one chip at a time through four charts that share a single slot.

## Context & Authority

**Why this story exists (Arjun, 2026-08-07, design session).** Story 4.1 shipped four metrics — BPM/tempo, genre diversity, key usage, and the library-conversion trend — multiplexed behind `MetricChipToggle` into **one** chart slot. At any moment 75% of what Epic 4 built is hidden, and the page reads as empty. Splitting the existing metrics into always-visible sections is ~4× the visible content for near-zero new computation — every trend series already exists in `styleEvolution.ts`. The second, load-bearing reason: **the trend lines are sparse-fragile and aggregate views are not.** The page-level `monthsSpannedAll < 2` gate currently blanks the *entire* page for a DJ with one month of history; summary tiles (this story) and, later, Story 4.8's aggregate charts read honestly off a single set — the cold-start property Decision B keeps forcing on Epic 4.

**RULED (Arjun, 2026-08-07): the library/digging metric MOVES to `/library-utilization`.** This closes Story 4.2's D-11, which was always a flagged assumption ("targets `/style-evolution` as a 4th chip pending Arjun's confirmation"), never a ruling. Rationale on the record: it's the only one of the four metrics about the DJ's *library* rather than their *playing*; Library Utilization was thin (one component, Story 4.3's meter); and putting the conversion **trend** next to the conversion **meter** ends the risk of the two disagreeing on screen. FR-10's PRD placement (§4.3 → §4.4) and FR-9 (sectioned composition + tile row) are already synced into `prd.md` — this is not a PRD-sync task for the dev agent.

**Story 4.8 depends on this story's section slots** (Genre and Key sections get a second chart each in 4.8) — do not restructure the section markup in a way that assumes only one chart per section.

**A real design gap this story must resolve, found during story creation, not by epics.md:** AC-3 says the moved trend and Story 4.3's meter must "share one window selection," but they do not share one today. `web/app/components/style-evolution/ConversionWindowToggle.tsx` (the trend's toggle) persists `curfew:style-evolution:conversion-window` over `CONVERSION_WINDOWS = [90, 60, 30]` days, default `90`. `web/app/components/library-utilization/LiveWindowDropdown.tsx` (the meter's dropdown) persists a *different* key, `curfew:library-utilization:conversion-window`, over `LIVE_CONVERSION_WINDOWS = [60, 30, 14]` days, default `60` — a structurally identical but independently-typed `useSyncExternalStore` copy (its own header comment says "copied rather than shared"). The two scales only overlap at 60/30. Task 3 below makes the call and records it — do not silently pick one without writing down which.

## Acceptance Criteria

Reproduced verbatim from `epics.md` Story 4.7:

1. **Given** the metrics currently multiplexed behind `MetricChipToggle`, **When** Style Evolution renders, **Then** they render as distinct stacked sections — **Tempo**, **Genre**, **Key** — each with its own heading and its own chart, all visible without interaction, **And** the chip toggle is retired rather than left present-but-inert. *(FR-9; the "a control that is present but inert is worse than one that isn't there" rule `StyleEvolutionView` already states for the library chip)*
2. **Given** the Month|Week granularity toggle and the low-confidence reveal, **Then** both become **page-level** controls acting on every trend section at once (not duplicated per section), retaining their persisted-selection behavior, **And** the now-orphaned persisted metric-chip key is explicitly migrated or removed from `localStorage` — never left as dead state a returning DJ's browser still carries. *(D-6; 4.1's own persisted-toggle pattern)*
3. **Given** the library/digging metric (Story 4.2), **Then** it moves to `/library-utilization` and renders alongside the Story 4.3 conversion meter — the same model (`buildLibraryConversion`), the same `ConversionWindowToggle`, no recomputation — **And** Style Evolution's subtitle copy drops its "library digging" clause, **And** the trend and the meter visibly share one window selection rather than each carrying an independent toggle that can be set to disagree. *(RULED 2026-08-07; closes Story 4.2's D-11)*
4. **Given** the page header, **Then** a summary tile row renders above the sections with four tiles — **median BPM**, **effective genre count** (2^H, the quantity 4.1's amended AC-5 defines as surfaced), **harmonic mix rate**, and **mix pace** — each showing the current period's value and its delta against the previous period. *(New; UX-DR17 stat-tile precedent from the dashboard)*
5. **Given** a DJ whose history has no previous period to compare against, **Then** each tile renders its value with **no delta at all** — never a fabricated `0%`, never a `—` that reads as a real measured flatline. *(Decision B cold-start honesty; D-8's "a gap, never a fabricated zero")*
6. **Given** **mix pace** (median seconds per track, from `SyncPlay.played_ms` — ~98% populated per Story 3.7 §3d), **Then** plays missing `played_ms` are excluded from the median **And** their count is disclosed alongside the tile, never silently folded in. *(Mirrors `no_genre_count`'s "never omitted" contract; SM-C1 graceful-fallback discipline)*
7. **Given** **harmonic mix rate** (`camelot_mixing_stats.compatible_transitions ÷ (compatible + incompatible)`, already synced on every set and currently plotted nowhere), **Then** `excluded_no_key` is disclosed the same way. *(Same discipline as AC-6)*
8. **Given** a DJ with ≥1 set but <2 months spanned, **Then** the page-level insufficient-history gate no longer blanks the whole page — the **summary tiles render** (they are aggregate, not time-series, and are readable off one set) while only the **trend sections** show the positive-framed insufficient state. *(AC-3/D-5 of Story 4.1, narrowed; UX-DR19)*
9. **Given** each section's chart, **Then** it ships its Chart Summary text-equivalent, and each tile is readable by a screen reader as value + delta + what the delta is against. *(UX-DR7, UX-DR21)*
10. **Given** 375px and 320px, **Then** sections stack, tiles reflow, no horizontal overflow, and every interactive target meets WCAG 2.2 AA SC 2.5.8's 24×24 minimum — **measured in a real browser against the DOM, not eyeballed from a screenshot**. *(4.1's review lesson, 2026-08-06; UX-DR21, UX-DR22)*

## Dev Notes

- **This is a `web/`-only story.** No `agent/` or `shared/` changes — `played_ms` and `camelot_mixing_stats` are already frozen, synced fields (Story 3.7 §3d and Story 1.7 respectively); this story is the first consumer of either in `web/`, not their introduction.
- **The single biggest risk is Task 3's window-scale reconciliation, not the new metrics.** The two new pure computations (mix pace, harmonic mix rate) are mechanically similar to `no_genre_count`'s existing disclosure pattern and low-risk to get right by following precedent. The conversion-window mismatch between `ConversionWindowToggle` (90/60/30) and `LiveWindowDropdown` (60/30/14) is a genuine, previously-undiscovered design gap that AC-3's "share one window selection" cannot be satisfied by wiring two independently-typed toggles to render side by side — resolve it explicitly (Task 3) before writing `library-utilization/page.tsx`'s new composition, or the work will need to be redone.
- **Follow Story 4.1's precedent for what NOT to relitigate.** Its D-9 through D-16 (Week/Month granularity, `2^H` presentation over raw entropy, in-chart category bars with `MAX_CATEGORIES = 5` + hidden-by-default "Other", dashed gap bridges never curved, dots always drawn not hover-only, two-way low-confidence reveal, year-labeling once the axis spans >12 months) are locked decisions this story inherits, not opportunities to reconsider while touching this code.
- **`useSyncExternalStore` is the house pattern for every persisted UI selection in this file family** (`MetricChipToggle`, `GranularityToggle`, `ConversionWindowToggle`, `LiveWindowDropdown` all use the identical module-scope-`sessionX`/`listeners`/`subscribe`/`getSnapshot`/`getServerSnapshot` shape). Whatever Task 3 lands on for the shared window control, follow this exact shape rather than `useState`+`useEffect` (Story 4.1's review specifically called out and fixed a `react-hooks/set-state-in-effect` lint violation from an earlier version of this pattern).
- **AC-8's gate narrowing is the story's other structurally important change.** Before: `monthsSpannedAll < 2` blanks everything via `page.tsx`'s single `model.monthsSpannedAll < 2 ? <InsufficientHistory /> : <StyleEvolutionView .../>`. After: the tile row always renders (given ≥1 set) and each of the three sections independently decides whether it has enough history to show its trend vs. its own insufficient state. Do not conflate this with the *0-sets* empty state, which is a separate, unaffected case.
- **No test-mocking or component-test convention exists yet for `StyleEvolutionView`/`ConversionRateMeter`/the toggle components** — confirmed at story creation, only `styleEvolution.test.ts`/`libraryConversion.test.ts` (pure-function suites) exist today. New component-level behavior this story introduces (the summary tiles' delta logic, the narrowed gate) should get unit coverage at the pure-function layer (`styleEvolution.ts`) where possible, per this codebase's established "logic in `lib/sets/*`, components stay thin" convention — do not feel obligated to invent a new component-testing harness as a side effect of this story unless the pure-function layer genuinely can't cover a behavior.
- **Re-read Story 4.1's Debug Log before starting file edits in this worktree.** That story lost most of a session to files being written against the wrong worktree path despite `EnterWorktree` having switched sessions — confirm all Read/Write/Edit calls resolve inside this story's worktree, not `/Users/arjun/Documents/name-pending` directly, before doing substantive work.

### Debug Log References

- **Real hydration bug found and fixed (not pre-planned, discovered during Task 8's real-browser pass):** `TrendChart.tsx`'s `pctX`/`pctY` helpers interpolated a bare `${(y / VIEW.height) * 100}%` into inline `style.top`/`style.left` — the full float64 shortest-round-trip string, up to ~17 significant digits. `effectiveDiversity`'s `2 ** bits` (feeding the Genre/Key sections' line-position math) is not guaranteed bit-identical across V8 builds (Node's SSR pass vs. the browser's V8) — legal per spec, transcendental math is implementation-approximated, not bit-exact. At 17 digits of precision this surfaced as a genuine SSR/hydration mismatch (`console.error`, "server rendered HTML didn't match the client properties") on **every single page load** of `/style-evolution`. This was invisible before Story 4.7: the Genre/Key metrics previously only ever rendered after a client-only chip click (no server/client diff possible for a client-only render). Sectioning them to always-visible-on-first-paint (AC-1) is exactly what surfaced it. Root-caused by comparing a fresh `curl` SSR fetch against the live post-hydration DOM value for the same dot in the same browser session (ruled out HMR/caching timing first). Fixed by rounding `pctX`/`pctY` to 4 decimal places (`.toFixed(4)`) — visually lossless (a 0.0001% error is a fraction of a sub-pixel at any real viewport) and matches the `.toFixed(2)` discipline this same file already uses for its SVG path strings. Verified fixed: repeated navigations to both pages showed 0 console errors/0 warnings after the fix, vs. 1 hydration error before it.
- **Second real finding during the same pass:** `.se-chart-other-toggle` (the "Show other" checkbox label, genre/key charts' catch-all-category toggle) measured 81×17px — below WCAG 2.2 AA SC 2.5.8's 24×24 minimum. Story 4.1's review had already fixed the sibling `.se-chart-info-btn` tap target via an invisible `::after`; applied the same fix shape here (`min-height: 24px` on the label, verified `81×24` via `getBoundingClientRect()` post-fix).
