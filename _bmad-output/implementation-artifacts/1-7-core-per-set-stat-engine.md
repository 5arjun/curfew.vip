# Story 1.7: Core per-set stat engine

Status: done

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As a DJ,
I want the agent to compute per-set stats arithmetically from the enriched plays,
So that accurate summaries and the energy arc render with no ML or cloud round-trip.

## Acceptance Criteria

1. **Given** an enriched set, **When** stats compute, **Then** it produces most-played tracks; most-played artists (**artist-tagged plays only** — no "Unknown" bucket, no untagged footnote); genre breakdown; BPM distribution; key/Camelot mixing stats; set length; track count. *(FR-6 foundation, CAP-5)*
2. **Given** the same set, **When** the energy-arc series computes, **Then** BPM-vs-timestamp points are produced. *(FR-7 foundation)*
3. **Given** any stat, **When** computed, **Then** it is arithmetic-only — no ML/inference is invoked. *(NFR-1, NFR-3)*
4. **Given** a ~5,000-track library and a typical set, **When** the full parse→enrich→stat pipeline runs, **Then** it meets concrete targets: a single set's stat computation ≤ 500 ms, a full-library pass ≤ 10 s (p95), agent idle CPU ≈ 0, and no UI-perceptible lag. *[TARGETS — confirm with Arjun, PRD §5.1/§12 `[ASSUMPTION]`, not yet locked]* *(NFR-1; Amelia's "no number = not a test", party 2026-07-20)*

### Scope boundaries (binding — read before writing code)

- **This story builds the first-ever per-play assembly step — own it deliberately, don't stumble into it.** Nothing before this story has ever combined `parser::Play` + `joiner::JoinedMetadata` + `genre::NormalizedGenre` into one record. Story 1.6 explicitly left "which raw genre wins when a play has both an inline `Play.genre` and a joined `JoinedMetadata.genre`" to "whichever stage assembles the final per-play record" (`joiner/mod.rs:33-38`, Story 1.6 Open Question #1) — **that stage is this story.** Build it as an explicit, named step (an `EnrichedPlay` type + an assembly function), not an implicit fold inside a stat-computation function, so the source-selection policy below is visible and testable in isolation.
- **Genre source selection (new decision this story must make — see Open Question #1 for the recommended default):** prefer `JoinedMetadata.genre` (already resolved through the full library → embedded-tag fallback chain, Stories 1.4/1.5) and fall back to `Play.genre` (the play-log's own inline tag, field 9 / `history_entry.genre`) only when `JoinedMetadata.genre` is `None`. Feed whichever raw string wins into `genre::normalize`. Never merge or concatenate the two; never guess a third value.
- **This story is `genre::normalize`'s first real consumer — its fold has known, logged gaps that will now surface visibly.** `deferred-work.md`'s "Deferred from: code review of 1-6" entry documents that `bucket_for`'s exact-equality match on a `trim().to_lowercase()` key mis-buckets several real-world genre shapes to `"Other"`: internal whitespace (`"deep  house"`), unlisted separator variants (`"drum&bass"`, `"r & b"`), typographic punctuation (curly apostrophes, en/em dashes), non-ASCII folding, and multi-value tags (`"House / Techno"`). That entry names **Story 1.7** (this story) as the trigger to refine the fold against a real Serato genre-string fixture. It is not a blocker — the outcome is always a safe "Other" mis-bucket, never a wrong bucket or a dropped play — but `genre_breakdown` (Task 2) is what will make these mis-buckets visible to a DJ for the first time. Do not silently absorb this into scope; if you touch the fold, bump `TAXONOMY_VERSION` per that entry's guidance. The same deferred-work section also logs two content gaps that will surface the same way: V1 taxonomy omissions (e.g. "melodic house", "organic house") and legacy ID3v1 numeric TCON `"(17)"`-forms mapping to `"Other"` instead of their decoded genre — both are logged product-content follow-ups, not this story's job to fix.
- **Key source selection (new decision — see Open Question #2):** prefer `Play.key` (the play-log's own field 51 / `history_entry."key"`, already Camelot notation per Story 1.2's field-confidence map and Story 1.3b's real-data confirmation) and fall back to `JoinedMetadata.key` (library join or embedded-tag fallback) only when `Play.key` is `None`. **`JoinedMetadata.key` is not guaranteed to be Camelot notation** when it came from an embedded ID3 `TKEY`/Vorbis `KEY` tag (`joiner/mod.rs:66-71` says so explicitly) — validate before using it for Camelot mixing stats (Task 3); an unparseable key is excluded from that stat, never fabricated into a wrong Camelot position.
- **BPM has no source-selection question.** `parser::Play` has no `bpm` field by design (Story 1.3 — BPM is scoped to the library join for both formats, confirmed again in `deferred-work.md`'s "Serato 4+ `join_session` — genre/key redundant, bpm still needed" entry). `EnrichedPlay.bpm` is `JoinedMetadata.bpm` directly, already `sane_bpm`-filtered (finite, positive) by the joiner.
- **No stable track identity exists for Serato 4+ sessions.** `parser::serato4::read_session` always leaves `Play.path: None` (`parser/serato4.rs:72`) — Serato 4+'s `history_entry` has no path column, and following `location_id`/`asset_id` into a join is explicitly out of scope (Story 1.4's carve-out, reaffirmed in `deferred-work.md`'s in-library entry). `joiner::embedded_tags::fill_gaps` takes `path: Option<&str>` as an argument but does not store it on `JoinedMetadata` either. **This means "most played tracks" cannot key on path alone** — it must fall back to a `(title, artist)` tuple identity when path is absent, which is the normal case for every Serato-4+-sourced play. This is a known, accepted collision risk (two different untagged remixes sharing a title+artist would count as one track) — do not build path resolution to fix it (that's Story 1.4's explicitly-deferred territory); log the limitation to `deferred-work.md` instead, per this project's standing discipline for known-but-unfixed gaps.
- **Segment detection (AD-17, FR-28) is explicitly out of scope for this story**, even though AD-17 says it "binds... the agent's stat-engine filter" and even though it will eventually live in this same module. The epics.md FR-coverage map routes FR-28 to **Epic 5** ("algorithmic segment suggestion... computed in the agent stat-engine"). This story's four ACs are the complete scope: per-set summary stats (AC-1), energy arc (AC-2), arithmetic-only (AC-3), performance (AC-4). Do not build windowing/density/BPM-floor/transition-smoothness logic here — that is Epic 5's job against this module later.
- **FR-27's confidence signal (Story 1.8, the very next story) is not this story's job either.** Story 1.7 computes descriptive stats over an already-known set of plays; Story 1.8 classifies the *session* as likely-live-vs-practice. Do not add a confidence field to any type this story introduces.
- **Persistence boundary — mirrors Story 1.6's.** There is no local store yet (that's Epic 2 Story 2.8, "Set capture into local sqlite") and no `shared/` sync contract carrying stats yet (Story 1.10 freezes that, and it is explicitly informed by *this* story's output shape per epics.md's Epic 1 design note b — "the `shared/` derived-payload/stat-output shape is designed against the Set Detail + Style Evolution UX... not blind"). This story's job **ends at producing typed in-memory stat values** from a `Vec<EnrichedPlay>`. Do not add fields to `shared/src/index.ts` / `shared/schema/sync-payload.schema.json`, and do not write to SQLite. Whoever builds Story 1.10 will read this module's output types as an input, not the other way around.
- **The exact shape of "genre breakdown," "BPM distribution," and "Camelot mixing stats" is a product/design decision this story must make a reasonable call on, not a spec already handed to you.** FR-6/epics.md name the four stats but do not define their wire shape (there is no UX-rendered component contract for them yet beyond "genre chips," "energy-arc-chart," and "chart-summary" in DESIGN.md). Ship a sensible, documented default for each (Task 2 gives concrete recommendations) and flag the shape for Arjun's confirmation (Open Questions #3-#5) — do not block implementation on it, exactly as Story 1.6 shipped a taxonomy content default and flagged it. The *mechanism* (arithmetic-only, deterministic, never-guessed) is what this story must get right; the exact field names/bucketing are cheap to adjust once Story 1.10 or the Set Detail UI actually consumes them.
- **AC-4's two numeric targets are not equally testable from inside this story.** The ≤500ms *single-set* target is this module's own responsibility and should be given a real (if generous, since the numbers are `[ASSUMPTION]`, unconfirmed) benchmark-style regression test. The ≤10s *full-library-pass* (p95) target spans the whole `parser → joiner → genre → stats` pipeline plus file I/O across ~5,000 tracks — no story has yet wired those stages together end-to-end against a real library (that wiring is watcher/capture territory, Epic 2 Story 2.8, or possibly Story 1.9's golden-file harness). Do not fabricate an end-to-end benchmark this story can't honestly run; log the gap to `deferred-work.md` instead (Task 5 has the concrete guidance). "Agent idle CPU ≈ 0" and "no UI-perceptible lag" are not unit-testable at all without a running watcher/UI — same treatment.

## Dev Notes

### The one genuinely new thing this story builds

Every prior Epic 1 story built a pure, single-purpose filter over an existing type (`joiner` resolves metadata, `genre` normalizes a string). This story is the first one that **assembles** — it is where `parser::Play`, `joiner::JoinedMetadata`, and `genre::NormalizedGenre` first meet as one record. Two source-selection decisions that Story 1.6 explicitly deferred (which raw genre wins; implicitly, which raw key wins) land here. Get `EnrichedPlay`'s construction right and named as its own step (Task 1) — do not let it dissolve into inline logic scattered across the stat functions, or the next story (1.8, or Epic 5's segment detection) will have no single place to hook into the assembled record.

### Pipeline placement

Documented pipeline (`lib.rs:4-8`): `watcher → parser → joiner → stat-engine → local store → sync-queue`. This story is the **stat-engine** filter — the fourth stage, and the first one that reads from *two* upstream filters at once (`parser` for `Play`, `joiner` for `JoinedMetadata`) rather than one. Nothing calls this module yet (no watcher exists), exactly as `joiner` and `genre` were built with no caller before them — this is normal for this codebase's build order (parser-first, riskiest-first, watcher/wiring later in Epic 2).

### Why the source-selection defaults are what they are

- **Genre: `JoinedMetadata` over `Play`.** `JoinedMetadata.genre` has already been through the *entire* Story 1.4→1.5 fallback chain (library lookup, then embedded-tag fallback) — it is the more deliberately-resolved of the two candidates. `Play.genre` is a bare play-log snapshot field with no fallback behind it. Preferring the more-resolved source when both exist, and falling back to the less-resolved one only when the better source is silent, maximizes real signal without guessing (AD-11) — it's a merge of two genuinely different raw observations, not fabrication.
- **Key: `Play` over `JoinedMetadata`.** Inverted from genre, deliberately: `Play.key` is confirmed Camelot notation at the source for **both** formats (Story 1.2 findings' field-confidence map for legacy; Story 1.3b's real-data confirmation that `history_entry."key"` is the same field Story 1.4's `joiner::serato4::join_session` also reads — see `deferred-work.md`'s "genre/key redundant" entry). `JoinedMetadata.key`, when it comes from the embedded-tag fallback, carries **no notation guarantee at all** (`joiner/mod.rs:66-71`). For a stat that specifically needs Camelot notation (not just "a key string"), prefer the source known to already be in that notation, and treat the other source as a lower-confidence fallback that must still pass Task 3's format validation before use.

### Frozen types this story must NOT change

- **`parser::Play`** (`parser/mod.rs:49-74`) — read-only input. Do not add fields.
- **`joiner::JoinedMetadata`** (`joiner/mod.rs:60-76`) — read-only input. Do not add fields.
- **`genre::NormalizedGenre`** (`genre.rs:228-241`) — read-only input, produced by calling `genre::normalize(...)` from inside this story's assembly step. Do not change its shape.
- This story's own new types (`EnrichedPlay`, `CamelotKey`, the various stat-output structs) are the only things it may freely design — there is no prior shape to preserve for them.

### Established idioms to follow (from Stories 1.3-1.6)

- **Infallible-by-design transforms** wherever a function has one correct answer for every input: `EnrichedPlay` assembly, `genre::normalize` (reused, not reinvented), `camelot::parse`, `camelot::compatible` are all total functions — no `Result`, no error enum. Reserve `Result`/panics-never for the same reason prior stories did: there is no UI-actionable hard-failure mode in arithmetic over already-validated data.
- **No `.unwrap()`/`.expect()` on production paths** — the consistent bar across every prior story; `.expect()` only in tests.
- **Raw/typed values preserved, never silently coerced** — e.g. don't stringify a `CamelotKey` back and forth if you can keep it typed through `mixing_stats`.
- **Heavy, rationale-first doc comments** — a `//!` module doc for `stats/mod.rs` naming the pipeline stage, the ACs it implements, its invariants (arithmetic-only, deterministic, never-guessed track/artist/genre counts), and what it deliberately does not do (no segment detection, no persistence, no `shared/` change, no confidence signal). Mirror `genre.rs:1-51` and `joiner/mod.rs:1-38`.
- **`#[derive(Debug, Clone, PartialEq)]`** baseline on new data structs; add `Eq`/`Default` only where they make sense (a `BpmDistribution` with `f64` fields cannot derive `Eq`; `EnrichedPlay` has no single sensible all-`None` default beyond what `#[derive(Default)]` would already give it structurally — your call per type, matching the reasoning `genre.rs` gave for skipping `Default` on `NormalizedGenre`).

### Real per-format gotchas discovered while preparing this story (read before designing `TrackIdentity`)

- **Serato 4+ plays never carry a `path`.** Confirmed by reading `parser/serato4.rs:72` directly (`path: None` is hardcoded, not conditional) — this is not a "sometimes missing" case, it is **always** true for every Serato-4+-sourced play in the pipeline as it exists today. Any design that assumes path is "usually available, occasionally missing" will misbehave on every Serato-4+ DJ.
- **`genre`/`key` are redundant between `parser::serato4::read_session` and `joiner::serato4::join_session` for Serato 4+** (both read the same `history_entry` columns independently) — this is already noted in `deferred-work.md` as confirmed, not a new finding, but it directly informs why the key-source-selection default above is safe: for Serato 4+, `Play.key` and `JoinedMetadata.key` are *the same value* read twice, so "prefer `Play.key`" costs nothing there; the fallback path only matters for the legacy format's off-library/embedded-tag case.
- **`JoinedMetadata.in_library` is `true` unconditionally for every Serato 4+ play** (`joiner/serato4.rs:63-74` doc comment explaining the assumption; the `in_library: true,` literal itself is at `joiner/serato4.rs:90`; tracked as a known spine deviation in `deferred-work.md`). This story does not use `in_library` for anything (no AC references it), but if a future refinement of these stats ever wants to slice by in-library/off-library, know that the Serato 4+ half of that slice is presently a guess, not a measurement.

## Open Questions / Assumptions
*(None block starting the story — reasonable defaults chosen; flagged for Arjun's confirmation before/during implementation.)*

1. **[DESIGN — recommend `JoinedMetadata.genre` first] Genre source-selection when a play has both an inline `Play.genre` and a joined `JoinedMetadata.genre`.** Story 1.6 explicitly deferred this to this story. Recommended default (Task 1, Scope Boundaries): prefer `JoinedMetadata.genre` (already resolved through the full library/embedded-tag fallback chain) and fall back to `Play.genre` only when the former is `None`. Confirm with Arjun, or flip the preference if he has a reason to trust the play-log's own snapshot more.
2. **[DESIGN — recommend `Play.key` first] Key source-selection for Camelot stats, analogous to #1.** Recommended default: prefer `Play.key` (confirmed Camelot notation at the source for both formats) and fall back to `JoinedMetadata.key` (not guaranteed Camelot; validate via Task 3's parser before use) only when `Play.key` is `None`.
3. **[CONTENT — needs Arjun] Exact shape of "genre breakdown."** Recommended: per-normalized-bucket counts plus an explicit no-genre count (Task 2). Confirm whether the UI eventually wants this folded into a single "Unknown" slice alongside `DEFAULT_BUCKET` ("Other"), or kept as three visually distinct categories (a real bucket, "Other," and "no genre at all") — this story ships the more granular, nothing-hidden version and lets a later story decide how to fold it for display.
4. **[CONTENT — needs Arjun] Exact shape of "BPM distribution."** Recommended: `{ count, min, max, mean, median }` (Task 2) rather than a pre-binned histogram — cheaper to compute, and binning is more naturally a chart-rendering concern for whichever web story consumes it. Confirm this is sufficient, or whether a binned histogram is wanted at the edge instead.
5. **[CONTENT — needs Arjun] Exact shape of "Camelot mixing stats."** Recommended: three counts (`compatible_transitions`, `incompatible_transitions`, `excluded_no_key`) over consecutive-pair transitions (Task 3), letting the caller derive a rate. Confirm this is the intended notion of "mixing stats" — an alternative reading could want per-play "how many of the *other* tracks in the set are Camelot-compatible with this one" (an O(n²) all-pairs stat, not a consecutive-transition one); the consecutive-transition reading is recommended as the cheaper, more standard DJ-facing metric (and the one consistent with how AD-17 already frames "transition" stats elsewhere in this codebase).
