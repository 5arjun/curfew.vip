# Story 4.11: Library roster sync — name the tracks the cloud can only count

Status: done

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As a DJ,
I want the tracks I own but haven't played to reach the cloud with their names attached,
so that the features that count them can also show me which ones they are.

## Context & Authority

**Why this is its own story, not folded into 4.4.** Three consumers need this, not one: Story 4.3's shipped conversion-rate meter (can say "34% converted" but not name the other 66%), Story 4.4's aging shelf (must render named rows with a prep-crate action — without this it renders hashes), and Story 4.10's search (search is scoped to played tracks only without it). A prerequisite serving three should not live inside one of them.

**Tier A only — this is the story's central, already-made decision, not something to re-litigate.** Cost was measured 2026-08-07 and it is asymmetric:
- **Tier A (title + artist): nearly free.** `DateAddedIndex::all_tracks()` (`agent/src-tauri/src/joiner/date_added.rs`) already returns `(path, date_added, title, artist)` for the whole library — `LibraryTrack.title`/`.artist` were added in Story 4.3 (Decision E-2) to compute `track_id`, and `capture::scan_library_adds` (`agent/src-tauri/src/capture.rs:299-360`) throws them away one line after hashing (the `filter_map` at line 310-322 keeps only `(id, added_at)`). This tier alone unblocks all three consumers.
- **Tier B (BPM, key, genre): parked, not in scope.** Those fields come from the joiner's per-track enrichment lookup, not from `all_tracks()`, so covering the *unplayed* catalogue means a real whole-library enrichment pass against NFR-1's ≤10s p95 full-library budget (`epics.md:327`). Tier B buys exactly one thing — the "you own 30% house, you play 12%" coverage-gap components — which are not part of this story. **Do not build Tier B. Do not add BPM/key/genre columns to the roster table or roster sync payload.**

**Decisions this story locks (all restated as ACs below, listed here so the "why" travels with the "what"):**
1. **Baseline add-dates must never reach cohort math.** `library_tracks.is_baseline = 1` rows already exist and are already excluded from `library_track_events` (AD-21, D-1) — this story must not accidentally create a second path (the new roster table) that leaks a baseline track's real pre-install `added_at` into any conversion computation. If it did, old months would retroactively populate against a still-go-forward numerator, read ~0%, and **silently change numbers the DJ has already seen**. This must be an invariant with a test, not a convention someone remembers.
2. **The roster is current-state and mutable; `plays` and `library_track_events` stay immutable as-played/as-added.** Today's `record_library_tracks` (`store.rs:919-940`) does `ON CONFLICT(track_id) DO NOTHING` — a re-tagged track (genre fixed, key set) never refreshes. The roster this story adds is the first place in this codebase where "current state, overwritten on re-scan" is the *correct* behavior, not a bug — because it describes what the DJ owns *now*, not a historical event. This divergence from the product's dominant as-played discipline must be written down where a future reader will find it (code comment + this story's Dev Notes), not left implicit.
3. **Deletions get a soft-absence marker, never a hard delete.** Nothing in the pipeline tracks removal today. Without this, Story 4.4's aging shelf would recommend prepping tracks the DJ already deleted. Recommended shape: an `absent_at` timestamp column, set when a previously-known `track_id` is missing from the current scan, cleared (`NULL`) if the track reappears — so a track that leaves and comes back keeps its identity and history rather than being re-baselined as new.
4. **Story 2.7's local-only raw-data boundary — already ruled, not open.** Ruled 2026-08-07 (Arjun, party mode): **acceptable**. `SyncPlay` already sends title/artist per play; this story is a change in *volume* (title/artist for the whole roster, not just played tracks), not a change in *category* (still no file paths, no raw library files, ever leave the machine). Do not re-raise this as an open question during implementation — implement per AD-22 (Task 5) and move on.
5. **AD-8's "agent's only write" rule gets its third sanctioned, named amendment: AD-22.** After AD-20 (status heartbeat) and AD-21 (library add-event batch), this is the pattern to copy exactly — a single `SECURITY DEFINER` RPC, one table, `dj_id` derived from `auth.uid()` never accepted as a parameter, no DJ write grant, idempotent, riding the existing `sync_queue::sync_loop` (no new poll loop). **Propose it explicitly in `ARCHITECTURE-SPINE.md` (Task 10) — do not land a third agent write quietly**, which is exactly the failure mode AD-8's own text warns against ("an unnamed third write is a violation of this rule, not a precedent set by the first two").

**A live, already-shipped gap this story closes as a side effect (AC-6).** `scan_library_adds`'s own doc comment (`capture.rs`, near the `LibraryScanOutcome` struct, ~line 230-246) concedes: a catalogued track with no resolvable title *or* artist is "silently excluded from this scan entirely." That's a live breach of the product's "never silently dropped" discipline (AD-11, the `no_genre_count`-style disclosure convention), and it's **already shipped** in Story 4.3 — it silently shrinks that story's conversion-rate denominator with zero disclosed count. `excluded_no_identity` is already computed on `LibraryScanOutcome` (`capture.rs`) but the doc comment on that same struct says it's "agent-local for now: no synced field exists yet ... currently visible via agent logs/tests only, not the dashboard" — and `watcher/mod.rs:582-583` discards the whole outcome (`.map(|_| ())`). This story is where that stops being true.

## Acceptance Criteria

1. **Given** the library scan, **Then** `title` and `artist` are persisted on `library_tracks` alongside the existing `track_id`/`added_at`/`is_baseline`, rather than discarded after hashing. *(`capture.rs:299-322`)*
2. **Given** the roster, **Then** it syncs to a new `dj_id`-scoped cloud table with RLS matching `library_track_events`, carried through the Story 3.3 offline queue, via an additive `shared/` type. **This is the third sanctioned amendment to AD-8's "agent's only write" rule** after AD-20 (heartbeat) and AD-21 (library events) — proposed explicitly as AD-22, never landed quietly. *(AD-3, AD-15, AD-8)*
3. **Given** D-1's baseline tracks, **Then** they **do** reach the roster (that is the point of this story) — and their `added_at` **must never reach cohort math**. The roster and `library_track_events` stay separate tables with separate purposes; a baseline track's real pre-install add-date entering the conversion cohorts would retroactively populate old months against a still-go-forward numerator, showing ~0% for cohorts that were simply never observed **and silently changing numbers the DJ has already seen**. State it as an invariant with a test, not as a convention. *(D-1; Decision B; the hazard this story most plausibly introduces)*
4. **Given** a track's tags change in Serato (a genre fixed, a key set), **Then** the roster reflects current state — today's `ON CONFLICT(track_id) DO NOTHING` never updates. **The roster is current-state and mutable; `plays` remain immutable as-played.** That divergence from the product's dominant as-played discipline is deliberate and must be written down, because the roster describes what the DJ owns *now*. *(`store.rs:919-940`)*
5. **Given** a track removed from the library, **Then** the roster records its absence rather than retaining it forever — otherwise the aging shelf will recommend prepping tracks the DJ deleted. Nothing in the pipeline tracks removal today; this story is where it is decided. **Recommendation: mark absent with a timestamp, never hard-delete**, so a track that leaves and returns keeps its history. *(New; no existing precedent to inherit)*
6. **Given** a catalogued track with no resolvable title *or* artist, **Then** its exclusion is **disclosed as a count**, not silent. `scan_library_adds`'s own doc comment concedes it is "silently excluded from this scan entirely" — which is a live breach of the product's "never silently dropped" discipline **already shipped in 4.3**, where it also silently shrinks the conversion denominator. Measure the real-library percentage while implementing; if it is material, it needs surfacing wherever the conversion number appears. *(AD-11; SM-C1; the `no_genre_count` contract)*
7. **Given** a first sync on a ~5,000-track library, **Then** it batches and degrades gracefully under the Story 3.3 queue rather than emitting one request per track or blocking the agent. *(NFR-1; AD-4's batching rationale in `SyncLibraryAddEventBatch`)*
8. **Given** this is the first time the cloud would hold a **full inventory of what the DJ owns** rather than only what they played, **Then** it is permitted against **Story 2.7's local-only raw-data boundary** — **ruled 2026-08-07 (Arjun, party mode): acceptable.** Rationale tested and held: `SyncPlay` already sends title/artist per play, so this is a change in *volume*, not in *category* — no file paths, no raw library files leave the machine. *(Story 2.7; AR-9; feeds Epic 6's privacy-policy work, ai-16)*
9. **Given** the new roster, **Then** Story 4.10's search widens from played tracks to the full library and its AC-2 empty-state copy is revisited — the ambiguity that AC exists to manage is exactly what this story removes. *(Story 4.10 AC-1/AC-2)*

> **AC-9 is not actionable today.** Story 4.10 is `backlog` and does not exist yet — there is no search component or AC-2 empty-state copy to revisit. Do not block this story on AC-9; instead build the roster's web-facing read seam (Task 8) so that whenever 4.10 is built, it reads the roster that already exists rather than needing its own agent/shared/cloud work. Note this explicitly in Completion Notes so whoever writes 4.10 doesn't have to re-discover it.
