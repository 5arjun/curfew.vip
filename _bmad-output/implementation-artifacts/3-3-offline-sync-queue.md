# Story 3.3: Offline sync queue

Status: review

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As a DJ,
I want a set completed while offline to queue locally and sync automatically on reconnect,
so that I never lose a set to a bad connection at the venue.

## Acceptance Criteria

1. **Given** no connectivity at set completion, **When** the set is captured, **Then** it queues in local SQLite. *(FR-4)*
2. **Given** connectivity returns, **Then** the queue drains automatically and idempotently (retries produce no duplicates). *(FR-4, AR-2/AD-4)*
3. **Given** the tray, **Then** it reflects "offline / queued" with a text-labeled glyph. *(UX-DR19 sync-offline, UX-DR23)*
4. **Given** two agents on one account draining the same shared-USB session (a rare multi-device / shared-USB edge persona), **When** both `PUT` the same `set_id`, **Then** MVP behavior is explicit **last-write-wins** on content columns — accepted as a deliberate MVP choice (not a silent gap); a writer-of-record rule is deferred and does **not** change the architecture spine. *(Ruling, party 2026-07-20 — Arjun)*

## Tasks / Subtasks

- [x] **Task 1: Drain loop — wire `sync_pending_sessions` into a live, periodic trigger** (AC: 1, 2)
  - [x] AC-1 is already structurally satisfied and needs no new code: `capture::build_serato4`/`build_legacy` (Story 2.8) already call `store::upsert_captured`, which leaves a `captured_sessions` row with `status = 'captured', synced_at = NULL` regardless of connectivity — that row *is* the queue (per AD-5, local SQLite is the durable offline cache; there is no separate queue table). Do not add a new table. Write a test/assertion in this story that names this explicitly (e.g. a comment or a short integration-style test in `sync.rs`/`store.rs` confirming a captured-while-offline row is indistinguishable from any other pending row) rather than skipping AC-1 as "already done elsewhere" — the story's own AC needs to be demonstrably true, not assumed.
  - [x] Add a periodic drain trigger that calls `sync::sync_pending_sessions` (`agent/src-tauri/src/sync.rs:222`, built by Story 3.2, currently called from nowhere per that story's own Dev Notes). Two wiring options, pick one and justify the choice in Dev Notes:
    - (a) Reuse `watcher::watch_loop`'s existing `RECONNECT_POLL_INTERVAL` tick (`watcher/mod.rs:39,363`, `rx.recv_timeout(RECONNECT_POLL_INTERVAL)`, 5s) — lowest-risk, no new thread, but 5s is aggressive for a *retry* cadence (see backoff note below) and couples an unrelated concern (drive-poll) to sync-drain timing.
    - (b) Spawn a second background thread from `lib.rs`'s `.setup()`, mirroring the exact pattern `watcher::start_watching(app.handle().clone())` already establishes at `lib.rs:419` (`std::thread::spawn` inside a `start_syncing`-style entry point in the new module, same shape as `watcher::start_watching` → `watch_loop`).
    - Recommended: (b), with its own longer interval (e.g. 30s), decoupled from drive-poll cadence — this avoids retrying a genuinely-offline connection every 5s (wasteful, and every failed attempt currently opens a fresh `reqwest::blocking` call up to its 15s timeout, `sync.rs:127`) and avoids overloading `watch_loop`'s already-multi-purpose tick with an unrelated responsibility.
  - [x] **Backoff, not a fixed-interval hammer.** Retrying a hard-down connection every N seconds forever is not "automatic drain," it's a spin loop. Implement a simple bounded exponential (or fixed-step, e.g. 30s → 60s → 120s → cap at 5min) backoff that resets to the base interval on a successful sync pass (`SyncSummary.synced > 0`, or transition from queued→idle). Keep it simple — this is not a distributed-systems problem, just "don't hammer a dead connection."
  - [x] **`SetIdMismatch` circuit breaker (deferred-work.md item, `sync.rs:89` comment, explicitly assigned to this story).** `SyncError::SetIdMismatch` is documented as "should never happen" but as of Story 3.2 nothing stops a deterministic mismatch from retrying forever at full cadence, indistinguishable from a transient offline failure. Classify errors from `sync_one`/`sync_pending_sessions` into at least two buckets: **transient** (`SyncError::Http` — network down, matches this story's actual "offline" scenario; `SyncError::Rejected` with a 5xx status) which the backoff loop retries, vs. **permanent/logic** (`SyncError::SetIdMismatch`, `SyncError::Corrupt`, `SyncError::MissingTimeBounds`, `SyncError::MalformedDjId`) which should not be retried at the same cadence — log loudly (already logged via `#[cfg(debug_assertions)] eprintln!`, `sync.rs:245-249`) and skip that row on subsequent passes rather than let one bad row spin the whole loop's backoff state forever. A simple per-row skip-list or a max-attempt cap on permanent-class errors is sufficient; do not over-engineer a full retry-policy framework.
  - [x] **`sync_pending_sessions` currently swallows per-row error detail into `SyncSummary { attempted, synced }`** (`sync.rs:182-186`) — there is no `failed`/`offline` field, and the loop only distinguishes transient vs. permanent via a debug-only `eprintln!`, not a return value the caller (this story's drain loop) can act on. You will need to either (a) extend `SyncSummary` with enough detail for the tray-state decision (e.g. `synced: usize, failed_transient: usize, failed_permanent: usize`), or (b) have the drain loop call a lower-level per-row function directly instead of `sync_pending_sessions` as a black box. Prefer (a) — it's a small, additive change to an existing struct, keeps `sync_one`'s row-level logic in one place, and Story 3.2's own module doc already anticipated this story extending its callers.
  - [x] **Concurrent-connection risk is now live, not hypothetical** (deferred-work.md, from Story 2.8's review, re-flagged live by Story 3.2's review): `store::open_at` (`store.rs:210-216`) sets no `busy_timeout`/`journal_mode=WAL` pragma. `watch_loop` already holds one long-lived connection (`watcher/mod.rs:182`, `store_conn`) for the loop's lifetime. If this story's drain loop opens a *second* `rusqlite::Connection` to the same `local.sqlite` file (likely, if wired as its own thread per the Task 1 recommendation above), a write collision is a real `SQLITE_BUSY` risk, not a future concern. Either (a) set `PRAGMA busy_timeout = 5000;` (or similar) and `PRAGMA journal_mode = WAL;` in `store::open_at` so any connection tolerates a brief lock wait, or (b) share `watch_loop`'s existing connection with the drain loop instead of opening a second one. Prefer (a) — it's a one-line schema-setup change that also protects against any *future* second-connection scenario, whereas (b) creates cross-module coupling between `watcher` and the new sync-drain code.

## Dev Notes

- **This story is agent-only. No Supabase migration, no `web/` changes.** The sync mechanism (RPC, idempotent upsert, content/overlay scoping) is entirely Story 3.2's — this story only adds *when/how often* that mechanism gets called and *what the tray shows* while it's not succeeding. AC-4's last-write-wins behavior already exists in the `sync_set` function's `ON CONFLICT DO UPDATE` (Story 3.2) — verify it, don't rebuild it. If AC-3's "dashboard status" half of UX-DR19's copy string (`"Queued — will sync when you're back online"`, `EXPERIENCE.md:86`) is read literally as also requiring a `web/` dashboard status line, that is **out of scope** for this story: there is no existing plumbing to expose local queue-depth/state to the cloud for a dashboard to render, and AC-3 as written only names "the tray." Flag this as a conscious scope call if Arjun disagrees.
- **The queue is not a new table — it's the existing `captured_sessions.synced_at IS NULL` state.** Per AD-5 ("local SQLite is a durable parse + offline cache, source of truth for a set only until it syncs") and Story 2.8's own schema comment (`store.rs:46`, `synced_at INTEGER -- NULL forever in this story; Story 3.2 owns setting it`). Do not add a `sync_queue` table — that would create a second source of truth to keep in sync with `captured_sessions` for no benefit.
- **`sync_pending_sessions` (`sync.rs:222`) already exists and is functionally complete for a single "attempt once" pass** — Story 3.2 built it, tested it, and explicitly deferred wiring it into anything live, precisely so this story could own the retry/backoff/trigger design without touching the underlying sync mechanics. Do not rewrite `sync_pending_sessions`'s core logic (auth token fetch, row iteration, `sync_one` call) — wrap/extend it (backoff loop calling it repeatedly; `SyncSummary` extended with more detail).
- **Three items were explicitly deferred from Story 3.2's code review straight to this story** (`deferred-work.md`, "Deferred from: code review of 3-2-idempotent-set-sync"): (1) no pagination/batching/cap on a sync pass — `rows_pending_sync` has no `LIMIT`, every eligible row gets one serial blocking HTTP call; if this matters at your target scale (a single DJ's per-night set count, likely 1-3 rows per pass) it's a nice-to-have `LIMIT`, not a hard requirement — use judgment, don't over-build. (2) `SetIdMismatch` circuit breaker — **addressed directly by Task 1's error-classification requirement above**, this is a correctness requirement, not optional. (3) No guard against concurrent/overlapping `sync_pending_sessions` calls (e.g. two agents/threads calling it at once) — the idempotent `ON CONFLICT` upsert makes this a redundancy/efficiency concern only (duplicate/racing network requests, not data corruption), consistent with AC-4's last-write-wins ruling; a guard is not required by this story's ACs, but do not introduce a *new* concurrent-call path (e.g. don't call `sync_pending_sessions` from both the drive-poll tick and a separate thread simultaneously) without at least a simple mutex/flag to avoid wasted duplicate HTTP calls.
- **Connectivity is inferred from `reqwest` error classification, not proactively detected.** There is no reachability/ping crate in this codebase (`Cargo.toml` confirmed — no `is-reachable`/`online`/similar), and none should be added for this story; a failed `SyncError::Http(reqwest::Error)` from an actual sync attempt *is* the offline signal (`reqwest::Error::is_connect()`/`is_timeout()` can help distinguish "can't reach host" from other HTTP-layer failures if useful for classification, but a blanket "any `Http` variant = transient/retry" bucket is acceptable and simpler). Do not add a separate "check connectivity" pre-flight call — it's redundant with just attempting the sync and reacting to the result.
- **`watch_loop`'s existing tray transitions must not regress.** `watcher/mod.rs:279` (`Idle` on drive-connect) and `watcher/mod.rs:328-331` (`DriveNotConnected` on drive-disconnect) are established, tested behavior from Stories 2.5/2.6. This story's new `Queued` transition must compose with these, not fight them — see Task 2's precedence-rule note. If both a drive-disconnect and a sync-queue-backlog are true simultaneously, prefer showing `DriveNotConnected` (it's the more actionable, more specific problem for the DJ) — document whichever precedence you choose.
- **Backoff should be simple.** This is a single-DJ desktop agent retrying a REST call, not a distributed system — a small fixed-step or exponential backoff (a few states, a cap) is sufficient. Do not add a new crate (e.g. `backoff`) unless the hand-rolled version becomes genuinely awkward; this codebase's established pattern (per Story 3.2's precedent) is small hand-written state machines with unit tests, not pulling in a library for a problem this bounded.
- **Testing conventions to follow** (established by Stories 2.8/2.10/3.2, no deviation expected): inline `#[cfg(test)] mod tests` per file; small `pub enum FooError` + manual `Display`/`std::error::Error` impls, no `thiserror`/`anyhow`; local test-double structs (`FakeAuthClient`, `FakeSyncClient`, `TempStoreFile` RAII guard — `sync.rs:337-421`) rather than a shared test-support crate or mocking framework; `#[cfg(debug_assertions)] eprintln!` is this codebase's convention for logging swallowed/non-fatal errors (already used at `sync.rs:245-249`, extend rather than replace).
