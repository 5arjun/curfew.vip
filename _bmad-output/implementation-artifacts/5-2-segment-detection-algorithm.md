## Story

As a DJ,
I want the agent to suggest segment boundaries from my session's timing patterns, calibrated to my own history,
So that splitting a set into meaningful parts starts from a smart guess, not a blank slate.

## Acceptance Criteria

1. **Given** a session, **Then** it is bucketed into fixed time windows with per-window play density, median BPM, and consecutive-pair BPM-delta smoothness computed. *(AR-13)*
2. **Given** a dancefloor candidate, **Then** it qualifies only if density + BPM clear floors calibrated per-DJ from that DJ's own history (never a global constant); adjacent candidates merge; a segment confirms only if transition-smoothness clears its own floor. *(AR-13)*
3. **Given** long no-play stretches, **Then** they mark an idle/gap. *(AR-13)*
4. **Given** a session, **Then** it may yield zero, one, or several dancefloor segments — never assume exactly one. *(AR-13, FR-28)*
5. **Given** a session spanning a DST transition, **Then** consecutive-pair time deltas stay non-negative and monotonic (the timeline is UTC-based), so per-window density and BPM-delta-smoothness are not corrupted by a repeated hour. *(Boundary's hole #2, party 2026-07-20)*

*(Source: `_bmad-output/planning-artifacts/epics.md` §Story 5.2, byte-identical. AR-13's substantive definition is AD-17 in the Architecture Spine — the AR-# tags themselves are the known-orphaned reference set, ai-13.)*

## Dev Notes

### Creation-time rulings D-19 – D-26 (continuing the design doc's D-1..D-18)

**D-19 — Transport: suggestions ride `SyncSetDerived` additively; `sync_set` materializes the rows. Proposed as AD-23.**
The design doc locks *what* the algorithm computes and *that* its writes land as `('suggested', false)` rows (§3f), but never resolves *how* agent-side output reaches a cloud table the agent is forbidden to write (AD-16: overlays "never written by the agent"; `shared/src/index.ts:49` explicitly says segments do "NOT appear in SyncPayload"; AD-8: "an unnamed fourth write is a violation"). Ruling: `suggested_segments` + `idle_gaps` become **additive optional fields on `SyncSetDerived`** (allowed post-freeze — the `subgenre_breakdown` precedent), and the existing sanctioned `sync_set` RPC materializes the segment rows cloud-side. Rationale: suggestions are *derived agent computation over content*, exactly what `derived` is for — the overlay property attaches to `confirmed`/`manual` state, which remains web-only. The `SyncLibraryAddEvent` doc comment's own test ("is it set-scoped? does re-send-on-re-sync make sense?") answers *yes* on both counts here — the inverse of the add-events case — so it belongs on the per-set payload, not a separate path. Rejected alternatives: (a) an AD-21/22-style separate RPC + queue item — creates an ordering race against the plays it FK-references and needs its own position→UUID resolution window; (b) a 6th `sync_set` parameter — leaves a live 5-arg overload to maintain for old agents, for no gain over (a strict subset of) the derived channel the payload already carries. **Consequence to guard:** `sets.derived` retains the agent's suggested-segments copy as inert provenance; after 5.3 edits rows it *will* diverge from the `segments` table. The web therefore never reads `derived.suggested_segments` — rows are the sole read model (enforced by doc comments in `shared/` and at the web read path). **AD-23 must be written in the Spine** (Task 6.1): sync_set's write scope extends to `segments` rows where `source = 'suggested' and not confirmed` only; confirmed/manual rows stay web-authored overlay, untouchable by any sync path; no DJ write grant is introduced.

**D-20 — Wire shape is 1-based positions; the RPC resolves, validates, and never lets a bad suggestion block content.**
The agent cannot know `first_play_id`/`last_play_id` — cloud `plays.id`s are minted (and re-minted, see D-21) inside `sync_set` itself. So the wire carries `first_position`/`last_position` against the same payload's `plays[]`, and the RPC resolves them after its own plays insert, in the same transaction. This also discharges, for the suggested-write path, 5.1's deferred review items "derive rather than trust" and "no ordering constraint": the RPC derives `set_id`/`dj_id` itself and position resolution makes `first <= last` checkable directly (the cross-write trigger 5.1 deferred is still not built — that remains with 5.3's write path). Invalid entries (out of range, inverted, non-integer) → `raise warning` + skip that entry: an overlay nicety must never poison the content sync or the retry queue (Epic 5's own charter: "nothing here is ever required for core dashboard stats").

**D-21 — Re-sync recomputes suggestions; and a real discovery: every re-sync currently wipes ALL segments rows — confirmed ones included, once 5.3 creates them.**
`sync_set` does `delete from public.plays where set_id = ...` + reinsert on **every** call (`20260731130000` line 60) — play UUIDs churn, and 5.1's `on delete cascade` FKs then remove every `segments` row for the set. 5.1's Dev Notes premise ("`plays` rows are not currently deleted by any shipped story") is **false** and has been since Story 3.2 (Task 6.3 corrects it on the record). For this story that behavior is *aligned with intent*: suggested rows should recompute on re-sync anyway, and the RPC makes the deletion explicit rather than cascade-incidental (Task 4.2). But the moment Story 5.3 writes a `confirmed = true` or `manual` row, any re-sync of that set (queue redelivery, backfill, Serato re-save) silently destroys DJ-authored overlay — a direct violation of AD-16's "an idempotent re-sync can never wipe an overlay." Not fixable here without redesigning the plays replacement strategy (stable upsert keyed `(set_id, position)`, or capture-and-rebind) — that redesign belongs to the story that creates the at-risk rows. Assigned forward loudly: Task 6.2's deferred-work entry, flagged as reachable-from-5.3.

**D-22 — The concrete numbers (the design doc's §5 open threads, closed as dev-time picks — all first-pass, all named `TUNE` constants in one block in `segments.rs`):**
- `WINDOW_SEC = 600` — carried from v0 unchanged (§5 thread: confirmed, not revisited without corpus evidence).
- `MIN_PLAYS_FOR_DETECTION = 6` — carried from v0 (below it: zero segments, zero idle gaps, matching v0's "not worth attempting").
- `FLOOR_PERCENTILE = 60` for all three floors — the design session's floated illustrative value adopted as the starting default. For density/BPM it is a lower bound (window must beat the DJ's 60th-percentile historical window); for smoothness it is an upper bound on median-|Δ| (run must be at least as smooth as the DJ's 60th-percentile window). One shared constant until evidence says the three signals need different percentiles.
- Priors (D-9: v0's retired constants become the blend prior): `DENSITY_PRIOR = 3`, `BPM_PRIOR = 118.0`, and `SMOOTHNESS_PRIOR_ABS_BPM_DELTA = 6.0` — new, since v0 had no smoothness signal; ~6 BPM is the outer edge of a beatmatched transition without a tempo ride, and AD-17's corpus observation (65–78% small-delta pairs in real mixed sets) brackets it. The least-grounded number in this story — validate against the golden fixtures and tune there, not in prod.
- Blend: `w = n / (n + BLEND_N)`, `BLEND_N = 5` — smooth shrinkage realizing D-9's "N ≈ 5 is where personal data carries real weight" as the half-weight point: session 1 → 17% personal, session 5 → 50%, session 20 → 80%, asymptotic to 1, no cliff anywhere. (Arjun's own 491-session backfill lands at w ≈ 0.99 immediately — effectively fully personal, which is the intent.)
- Idle (D-10/D-11, §5 threads): a stretch is **idle** when true inter-play silence (last timed play before → first timed play after) `>= IDLE_LABEL_MIN_SEC = 600`; labeled idle gaps are emitted as `idle_gaps` (descriptive only, never a gate — a zero-play window already fails candidacy on density). Bridge tolerances: an ordinary sub-floor gap of ≤ 1 window bridges (v0's `GAP_MERGE_WINDOWS = 1`, kept global for now — §5's "maybe per-DJ" thread explicitly not taken); but any gap whose true silence `> IDLE_HARD_BREAK_SEC = 1200` **hard-breaks**, even when it fits inside a single bridgeable window. That elapsed-time formulation is what makes idle's threshold genuinely *shorter* than the regular bridge (a 1-window gap can hide up to ~30 min of dead air between its bounding plays — the dinner break v0 would happily bridge); it realizes D-11's short-bridges/long-breaks split with real time, not window counts.
- Smoothness pair convention (within D-6's intent): a consecutive-pair delta needs both plays' BPM; each pair is assigned to the window containing the **second** play's start (counted once, no boundary double-count). Run confirmation: median over the run's windows' `median_abs_bpm_delta` values (windows with no delta data excluded; a run with zero delta data passes vacuously — AD-11's never-guess).
- `WHOLE_NIGHT_FRACTION` **dropped**: v0 returned `null` when the run ≥ 90% of the night because its only consumer wanted a stats *cut* and no-cut was the honest UI fallback. In the row model, "the whole night was dancefloor" is a true, useful suggestion (5.3 will render and edit it), and web stats scoped to it are identical to whole-set stats by construction — nothing is forced (Task 5.3 covers the web behavior).

**D-23 — Calibration pool: chronological, live-computed; no confidence filter (corrected at validation).**
Pool for a session = per-window `WindowStats` from captured sessions **strictly earlier** than it (`started_at`, tiebreak `session_identity`), excluding only sessions below `MIN_PLAYS_FOR_DETECTION` (a 2-track cue-up contributes garbage windows). **A confidence-based practice filter was drafted here and struck at validation:** `confidence.rs` is explicit that its value is *symmetric classifiability*, "not a live/practice probability" — sparse long-gap bedroom previewing scores **1.0** (would pass a `< 1.0` filter) while a tight gapless club set scores **0.2** (would be excluded), the exact inverse of the intended filter. No directional live/practice signal exists agent-side today, so the pool takes everything above the plays floor. *Known, accepted limitation:* a heavy-practice DJ's sparse windows pull the P60 floors down somewhat; the P60-over-all-windows placement plus the D-9 prior blend damp this, and the correct future fix is a real directional signal (Story 1.8's open ceiling question, ai-21) — never a repurposed symmetric one. *Why chronological rather than all-history:* determinism under re-derivation. `backfill_captured_serato4` re-derives every captured row at launch and re-queues on any change — floors computed from "all history now" would shift with every new capture, silently rewriting suggestions (and downstream card stats) the DJ has already seen, and re-queuing 491 sets every launch. With predecessor-only pools a re-derive is byte-stable (Task 2.4 asserts it), each historical session is calibrated against what actually preceded it, and new sessions always use full history. Live rollup, no persisted profile — D-16 honored; if profiling shows the prefix computation matters it can be memoized in-process, never durably.
