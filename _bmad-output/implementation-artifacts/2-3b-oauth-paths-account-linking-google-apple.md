# Story 2.3b: OAuth paths + account linking (Google, Apple)

Status: done

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As a DJ,
I want to sign in with Google or Apple and land on my one account,
so that my provider choice never forks me into duplicate identities.

## Acceptance Criteria

1. **Given** Google or Apple sign-in, **When** the verified email matches an existing `dj`, **Then** it links to that same account (idempotent on verified email). *(FR-29, AR-10)*
2. **Given** Google or Apple sign-in with a new verified email, **When** it completes, **Then** a `dj` account is created idempotently. *(AR-10)*
3. **Given** distinct verified emails across providers, **Then** they are **not** auto-merged in v1. *(AR-10)*

[Source: _bmad-output/planning-artifacts/epics.md#Story 2.3b, lines 411-421]

### Scope boundaries (binding — read before writing code)

- **In scope:** Google OAuth sign-in, Sign in with Apple, the OAuth callback route (code-exchange), and confirming/documenting that cross-provider account linking on verified email is correct. **Out of scope:** the post-OAuth phone-required prompt (Story 2.3c — do not add a `phone` column or prompt here, same column-sequencing rule Story 2.1/2.3a already established), any visual polish (official Google/Apple button lockups, Ghost-style chrome — Story 2.4), and the "Enable Passkey" post-sign-in nudge (FR-29 scopes passkey as an add-on to the **email-based path** specifically — do not extend `EnablePasskeyPrompt` to OAuth sign-ins in this story; an OAuth callback is a full-page navigation away from `/login` and back, not a client-state transition, so it structurally would not hit that prompt anyway unless deliberately wired to).
- **Account linking is native Supabase Auth behavior — do not build it.** Verified live against Supabase's own docs (2026-07-27): GoTrue automatically links a new OAuth identity to an existing user whenever both share the same **verified** email — no code, no config flag. It also automatically strips any other *unconfirmed* identities off that existing user at link time (anti-account-takeover). This directly satisfies AC-1: once the provider's OAuth callback completes and `exchangeCodeForSession` runs, the resulting `auth.users` row **is** the right one — there is no separate "look up and merge" step to write. AC-2 (new email → new account) is *also* already covered: Story 2.1's `handle_new_dj()` trigger (`AFTER INSERT ON auth.users`) fires on any new `auth.users` row regardless of which provider created it, exactly as it already does for email+password (2.3a). **Do not add a second account-provisioning path** — same rule 2.3a already established for its own AC-1.
- **`enable_manual_linking` in `supabase/config.toml` (currently `false`) is a *different* feature — do not touch it.** It gates `linkIdentity()`, a beta API letting an *already signed-in* user explicitly attach a provider with a **different** email to their account. That's not what AC-1/AC-2 need (both are same-verified-email auto-linking, which needs no flag) and building a "manage linked identities" UI is not in this story's ACs.
- **AC-3 is a negative/no-op assertion, not new logic.** "Not auto-merged" is what happens by default when two providers carry genuinely different verified emails — GoTrue creates two separate `auth.users` rows, Story 2.1's trigger creates two separate `djs` rows, and nothing in this story's AC-1/AC-2 scope touches that. Confirm it (a real end-to-end check if credentials allow, or a documented statement in the Dev Agent Record if they don't — see the credentials note below) rather than writing merge-prevention code that doesn't need to exist.
- **⚠️ Real external-provider credentials are required to test either OAuth path end-to-end — and this coding agent almost certainly does not have them.** Unlike 2.3a (email+password, passkey), which only ever talked to the **local** Supabase stack, Google and Apple sign-in both require a real registered OAuth application talking to Google's/Apple's actual servers, even against `supabase start`'s local Auth server:
  - **Google**: a free Google Cloud Console OAuth 2.0 Client ID + secret, with `http://127.0.0.1:54321/auth/v1/callback` (the *local Supabase API's* callback, not the Next.js app's route) registered as an authorized redirect URI. No paid account needed; a developer can self-serve this in a few minutes.
  - **Apple**: an active Apple Developer Program membership (**$99/year** — per Epic 2's cross-cutting note, this enrollment was flagged as a day-zero parallel procurement action for AR-14 code-signing; check with Arjun whether it's done and whether it also covers a **Services ID with Sign In with Apple enabled**, which is a separate configuration step from the code-signing identity), plus a `.p8` signing key used to hand-generate an ES256 JWT as the `client_secret` (expires every 6 months — this is not a one-time credential like Google's).
  - **Do not attempt to fabricate, mock, or skip past this requirement.** If credentials are not available in this environment, implement the full code path (below), get it to build/lint/typecheck clean, and **flag incomplete manual E2E verification in the Dev Agent Record** exactly as 2.3a flagged its un-completable passkey ceremony (Task 5.4/8.2d) — do not claim AC-1/AC-2/AC-3 are human-verified if the real provider round-trip was never actually driven.

### Latest technical specifics (web research, 2026-07-27)

- **Automatic identity linking (Supabase Auth docs, `auth-identity-linking`, fetched 2026-07-27):** GoTrue links a new OAuth identity to an existing user automatically whenever both carry the same **verified** email — this is unconditional default behavior, not something enabled by a project setting. On link, GoTrue also **removes any other unconfirmed identities** already on that user (anti pre-account-takeover measure) — informational, not something this story needs to code around. Manual linking (`linkIdentity()`, different-email case) is a **separate, beta** feature gated by `enable_manual_linking`/`GOTRUE_SECURITY_MANUAL_LINKING_ENABLED` — not used by this story.
- **Google OAuth local config (Supabase docs, `social-login/auth-google`, fetched 2026-07-27):** `supabase/config.toml` needs a new `[auth.external.google]` block (`enabled`, `client_id`, `secret = "env(...)"`, `skip_nonce_check`) — confirmed this project's config.toml has **no existing Google block at all** (read directly, 2026-07-27), unlike Apple's block which already exists disabled. If multiple Google client IDs exist (web/iOS/Android), the web client ID must be listed first in a comma-joined `client_id` string — not relevant unless a future story adds native clients.
- **Apple OAuth setup (Supabase docs, `social-login/auth-apple`, fetched 2026-07-27):** the `client_secret` is **not a static string** — it's a hand-generated ES256-signed JWT built from a `.p8` private key (downloaded once from the Apple Developer portal), the Team ID, the Key ID, and the Services ID (`client_id`), and it **expires every 6 months**, requiring manual regeneration (no auto-refresh). This is a real, recurring operational dependency outside this story's code — flag it for Arjun rather than treating it as a one-time setup cost.
- **`signInWithOAuth()` client behavior:** in a browser context it performs the redirect to the provider itself (`window.location`) unless `skipBrowserRedirect: true` is explicitly passed — this story does not pass that flag, so no manual `redirect()`/`window.location` call is needed after invoking it.
- **OAuth callback URL is two-hop, don't confuse the two:** the redirect URI registered *with Google/Apple* is Supabase's own Auth server (`http://127.0.0.1:54321/auth/v1/callback` locally) — **not** this app's `/auth/callback` route. GoTrue itself completes the provider exchange, then redirects to *this app's* `redirectTo` URL (`/auth/callback`) with its own `?code=` param for the app to exchange via `exchangeCodeForSession`. Registering the wrong URL with Google/Apple (e.g. `localhost:3000/auth/callback` instead of `127.0.0.1:54321/auth/v1/callback`) is the most common setup mistake per the docs surveyed.
