# Story 1.2: Parser-validation spike against real sessions

Status: review

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As a product owner,
I want a throwaway spike that runs the candidate `.session` parsing approach against the riskiest real Serato session types before we commit the full pipeline,
So that the clean-room implementation is validated against reality and the frozen contract is de-risked (SM-1).

## Acceptance Criteria

1. **Given** at least one real multi-track wedding session, one USB-hosted-library session, and one WAV-heavy-library session, **When** the spike runs, **Then** it emits parsed play counts + track identities per session and a written go/no-go with observed format quirks. *(Design note a, NFR-5)*
2. **Given** the spike output, **When** compared against ground truth (Serato's own display or the DJ's recollection), **Then** every discrepancy is enumerated and classed as parser-fixable or format-limitation.
3. **Given** the spike concludes, **Then** its learnings are recorded as explicit inputs to the `shared/` contract shape (Story 1.10) — the contract is not frozen before this. *(Design note c)*
4. **Given** the spike concludes, **Then** its code is explicitly **throwaway** — Stories 1.3–1.7 build the production parser fresh; the spike is never extended into production. *(Winston, party 2026-07-20)*

This is a **throwaway spike**, not the production parser. Its only job is to run the candidate `.session`-parsing approach against real, risky Serato data *before* Story 1.3 commits a production clean-room parser and *before* Story 1.10 freezes the `shared/` contract. Nothing built here ships; its output is a written go/no-go plus concrete learnings that feed 1.3 (implementation approach) and 1.10 (contract shape). Resist the urge to make this production-quality — AC-4 explicitly forbids extending it.

### `.session` is NOT a format `triseratops` parses — confirmed via the crate's own docs
Verified against `docs.rs/triseratops` (2026-07-21): the crate exposes exactly three public modules — `error`, `library` (Serato library DB / crates — includes `database V2`), and `tag` (Serato's file-tag metadata — hotcues, beatgrids, waveform, across ID3/FLAC/MP4/Ogg Vorbis). **No module or mention of `History/Sessions/*.session` parsing exists in the crate.** This confirms exactly what `ARCHITECTURE-SPINE.md` AD-11 already implies by calling for a **separate** "clean-room Rust `.session` parser" alongside `triseratops` — the play-log format is the one artifact nothing off-the-shelf reads, which is *why* this story exists as a spike rather than "wire up a crate." `triseratops` is still directly useful here for the `library` (database V2) half of Task 3/AC-1's cross-checking, and its `tag` module may overlap with what the standalone `id3` crate provides — no need to duplicate both for library-DB tag reads.

### Clean-room discipline — what's fine to read, what isn't
AR-5 requires a **clean-room** `.session` parser. Public research on Serato's broader binary envelope exists (Mixxx's wiki documents the `.crate`/database format as: each record = 4-byte ASCII tag + 4-byte big-endian `u32` length + payload, with `o*` tags holding nested records, `t*`/`p*` holding UTF-16BE text, `u*` holding 32-bit BE integers). Reading *format documentation* like this to understand the general envelope shape is fine — it's factual/structural, not copyrightable expression. **Do not port or transcribe code** from Mixxx (GPL) or any other existing `.session`/history parser implementation (e.g. the TypeScript `seratolibraryparser` or Go `seratoparser` projects that also claim history-file support) — write the actual decode logic from this spike's own hex-dump analysis of the real `.session` files in the corpus above. The question this spike must answer empirically is whether `.session` reuses that same tag/length/payload envelope — treat that as a hypothesis to test against real bytes, not an assumption to code against blindly.

### `id3` crate WAV support — the open question is data, not the crate
Verified against `docs.rs/id3` (2026-07-21, v1.17.0): the crate explicitly supports **"MP3, WAV and AIFF files"** — WAV/RIFF-embedded ID3 is a first-class supported container, not a gap in the crate. The real open question (architecture's still-open item #3, `SOLUTION-DESIGN.md` §8) is whether real-world WAV files in a working DJ's library actually *carry* embedded tags at all (many WAV rips/downloads ship with none) — that's exactly what Task 3/4's WAV-heavy test case needs to measure and report, not a library-capability risk.

No CI wiring and no unit-test bar apply here (this crate is invisible to CI by construction — see Task 2). "Validation" for this story *is* Task 4's empirical comparison against ground truth, captured in the findings doc from Task 5. A `cargo test` suite is optional and not required for the ACs to pass; don't over-invest in spike test scaffolding that will be thrown away with the rest of the crate.
