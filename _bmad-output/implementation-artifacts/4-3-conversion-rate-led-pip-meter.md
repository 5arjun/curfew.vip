# Story 4.3: Conversion-rate LED-pip meter

Status: done

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As a DJ,
I want my conversion rate — % of added tracks played ≥1 time over a rolling 90-day window — as an LED-pip meter,
so that I can gauge how much of my library I actually use.

## Context & Authority

Two product decisions were made live during this story's creation, both recorded here as binding rather than left for the dev agent to re-derive or guess:

**Decision E-1 (meter semantics).** AC-1's plain text — "% of tracks added to the library **in the last 90 days** that have been played ≥1 time" — describes a **live, current-window** stat: denominator = tracks whose `added_at` falls within the trailing 90 days as of *now*; numerator = however many of those have been played at all, whenever that play landed. This is a **different metric** from what `libraryConversion.ts` (Story 4.2) computes: 4.2's cohort trend measures whether a play landed *within* a track's own 90-day window after its add-date, and it deliberately **excludes** any cohort whose window hasn't fully elapsed yet (`isCohortComplete`) — i.e., 4.2 structurally omits exactly the tracks 4.3's meter is about. Do not implement the meter by reading `model.windows[90]` and averaging/summing its `cohorts` — that reports on cohorts from ~3+ months ago, not "the last 90 days." This story adds a **new** function alongside the existing cohort model (see Task 4).

**Decision E-2 (track identity).** `deferred-work.md` (line 262, still open) documents a measured, real problem: `track_id` is `fnv1a_hex` of the volume-root-relative path, so the same song on a laptop drive and a gig USB hashes to two unrelated identities — on Arjun's own real data this produced whole 0% cohorts for months he demonstrably played music (2,115 of 2,294 in-library plays resolve from a drive other than the one the boot-drive catalogue export saw). `ARCHITECTURE-SPINE.md` AD-21 (line 196) already anticipates the fix and pre-clears it: *"§194's identity clause is being rewritten separately as part of the title+artist identity switch and does not need re-ratification once updated."* **This story implements that switch**: `track_id` moves from a path hash to a normalized-title+artist hash, for both the library-scan side and the play-capture side. This is Task 1, and it is a prerequisite for Task 4/5's numbers to be meaningful — do the identity fix first, or the meter you build will read the same deflated data 4.2's chart already does.

## Acceptance Criteria

1. **Given** a rolling 90-day window, **Then** conversion rate = % of tracks added to the library in the last 90 days that have been played ≥1 time in a set is computed. *(FR-11 — window length confirmed 2026-07-21, Arjun; semantics per Decision E-1 above)*
2. **Given** the display, **Then** it renders as filled/empty square "pips" (hardware-LED-meter style), not a bar or a bare percentage. *(UX-DR11 — reuse the shipped pattern, see Dev Notes)*
3. **Given** the metric, **Then** the 90-day rolling-window definition is shown so the number is interpretable.
4. **Given** a library track missing both `tadd` and `uadd` (~6% of tracks, per Architecture Spine Open Questions #2), **Then** it is excluded from the conversion-rate denominator and disclosed via a distinct "Unknown add-date" count — never silently folded into the computed percentage. *(Architecture Spine OQ#2 graceful-fallback requirement; SM-C1)*
5. **Given** the `/library-utilization` route, **Then** the meter renders there (replacing the Story 3.5 throwaway stub), not on `/style-evolution` — Story 4.2's trend chart already claimed the Style Evolution chip slot (D-11); the pip meter is Library Utilization's own first real content. *(sprint-status.yaml "WHAT 4-3 STILL OWES"; epics.md §4.4 grouping)*
6. **Given** the identity-fix scope (Decision E-2), **Then** `track_id` is derived from normalized title+artist for both newly-captured plays and newly-scanned library tracks, and `ARCHITECTURE-SPINE.md` AD-21's identity clause (line 194) is updated to describe the new derivation, per its own pre-clearance. *(deferred-work.md line 262; AD-21 line 196)*
