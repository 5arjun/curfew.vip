# Story 2.7: Local-only raw-data boundary

Status: done

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As a DJ,
I want the agent's filesystem access scoped to only my configured Serato path, and raw files never to leave my machine,
so that my private library data stays local by construction.

## Acceptance Criteria

1. **Given** the agent, **Then** its filesystem capability is scoped to the configured Serato path only (not broad disk access). *(FR-3, NFR-2)*
2. **Given** any network transmission, **Then** raw `.session` files and the raw library DB are never sent off-machine — only derived/structured data leaves, over HTTPS. *(FR-3, NFR-2)*
3. **Given** a contract test on the outbound payload, **Then** it asserts no raw-file blob is present. *(AR-1)*

  - Wire this guard into the two call sites that read Serato-owned catalogue data from a configured root: `joiner::legacy::LegacyLibrary::load(library_root)` (`agent/src-tauri/src/joiner/legacy.rs:98`, currently `std::fs::read(&path)` with no scope check) and `joiner::serato4::open_read_only(path)` (`agent/src-tauri/src/joiner/serato4.rs:33`). Both currently trust their caller's path unconditionally — this task adds the check, it does not change their read logic or error types beyond adding the new scope-check failure mode (extend each module's existing error enum with a new variant, matching this crate's no-`anyhow`/`thiserror` convention — see `JoinError` in `legacy.rs`).
  - **Do not apply this guard to `joiner::embedded_tags::read_embedded_tags`/`fill_gaps`** (`agent/src-tauri/src/joiner/embedded_tags.rs:77,108`). This is deliberate, not an oversight: a played track's own audio file (`parser::Play.path`) is sourced from the DJ's Serato history and can legitimately live anywhere on disk the DJ's music library does (a different folder, a different drive) — it is not "broad disk access," it is reading the one file a real, already-logged play refers to. Confining this read to the Serato root would break Story 1.5's existing, shipped fallback. Document this exception inline in `fs_scope.rs`'s module doc comment (one sentence, pointing back to this story) so a future reader doesn't "fix" it by wrapping this call too.
  - **Do not touch `watcher::detect::classify`/`scan_removable_volumes`** (`agent/src-tauri/src/watcher/detect.rs`). Its reads are bounded `Path::is_file()` existence checks against a fixed, small set of relative marker filenames (`database V2`, `master.sqlite`) under a *candidate* root being evaluated for confirmation — not content reads, and not the "configured path" this AC governs (there is no configured path yet at detection time; that's the whole point of detection). Story 2.6's own Dev Notes already carved this distinction out by name: "the scan step ... must read outside the eventual configured path to find it in the first place; that tension is exactly why Story 2.7 exists as its own story, not a reason to skip scanning." Adding scope-restriction here would break first-run detection, not harden it.
  - Unit tests (temp-dir fixtures, mirroring `settings.rs`'s `TempSettingsFile`/`joiner/legacy.rs`'s existing fixture pattern): a path inside the configured root passes; a path outside it (sibling directory, `../` traversal, an absolute unrelated path) is rejected; a path that escapes via a symlink pointing outside the root is rejected (canonicalize before comparing — `Path::starts_with` on non-canonicalized paths is not a security boundary).
  - Note in Dev Notes/Completion Notes: this guard has no caller yet in the live `.setup()` startup path, because nothing calls `LegacyLibrary::load`/`open_read_only` from production code except `watcher::mod.rs`'s `check_for_new_sessions` (which already only ever passes the one path the DJ confirmed — the guard is defense-in-depth there, not fixing a live bug). - **Why AC-1 cannot mean "the agent may only ever open files under one folder" literally:** `parser::Play.path` (a played track's file path, sourced from the DJ's own Serato history) can point anywhere on disk — the DJ's music library is very often not stored inside `_Serato_`/next to `master.sqlite`. Story 1.5's embedded-tag fallback (`joiner::embedded_tags`) already legitimately reads that path directly. AC-1's real target is the **catalogue reads** (the library DB, the session log) — those must stay inside the configured root — plus not scanning arbitrary parts of the disk beyond narrow, bounded, already-shipped detection. See Task 2 for the exact call-site-by-call-site breakdown; do not "fix" the embedded-tag path by scoping it too, that would regress Story 1.5.

- **Why Tauri `capabilities/default.json` is not the enforcement mechanism:** confirmed by Story 2.6's own Dev Notes and this crate's actual setup — Tauri's capability/permission system (`agent/src-tauri/capabilities/default.json`, currently `core:default` + `dialog:allow-open`) gates only what the **webview** can invoke over IPC. All Serato/library/session file access happens in Rust backend code via `std::fs`/`rusqlite` directly, which capabilities do not restrict at all. There is no `fs:` plugin permission in use and none is needed for this story — do not add one expecting it to do this job; it would gate nothing relevant (the webview never touches these paths) while adding an unused permission surface. The guard from Task 2 is a **code-level invariant** (a Rust function every catalogue-read call site must go through), not a config change.

- **Architecture governance (read `ARCHITECTURE-SPINE.md` AD-2 in full — this story is its direct implementation):** "raw `.session` files and the raw library DB never leave the machine... Only a derived, normalized JSON document per set crosses the wire... Agent filesystem access is capability-scoped to the configured Serato path only." AD-3 (the `shared/` versioned contract) and AD-16 (content-only agent upsert, overlay columns disjoint) are the sibling invariants that make AC-3's contract test meaningful — the schema is already `additionalProperties: false` throughout (frozen by Story 1.10) and deliberately excludes `EnrichedPlay.path` from the wire shape (see `shared/src/index.ts`'s own doc comment on `SyncPlay`, and `deferred-work.md`'s "Raw file `path` deliberately excluded..." entry). This story's job is to write the **regression test** that pins that already-correct design decision, not to redesign the schema.

- **Error-handling idiom (repo-wide convention):** a small enum with `Io`/format-specific variants, `Display` + `std::error::Error` impls, no `anyhow`/`thiserror` — see `SettingsError` (`settings.rs`), `ParseError` (`parser`), `JoinError` (`joiner/legacy.rs`). The new `fs_scope` guard's error type should follow this exact shape.

- **Testing conventions:** temp-dir fixtures with a `TempDir`/`Drop`-cleanup helper (see `watcher/detect.rs` and `watcher/mod.rs`'s near-identical `TempDir` structs, and `settings.rs`'s `TempSettingsFile`) — mirror this pattern for the new `fs_scope` tests rather than introducing a new fixture style or a crate like `tempfile` (not currently a dependency; the existing convention hand-rolls a unique-per-test scratch dir under `std::env::temp_dir()`).

- [x] [Review][Patch] `fs_scope` guard is a no-op for the common Serato 4+ configuration (`root == candidate`) — AC-1 unenforced in the primary case. **Resolved (Arjun, 2026-07-29): scope against the parent directory when root is file-shaped.** `watcher::detect::classify` gained a branch letting `root` be the literal `master.sqlite` file. Since `install_path()` renders a Serato4 confirmation as that same literal file path, `settings.serato_path_override` stores it, and `watch_loop` reads it back as `current_path`. `check_for_new_sessions(path, db_path, ...)` then calls `open_read_only(root=path, path=db_path)` with `root` and `candidate` the identical `PathBuf` — `ensure_within_root` canonicalizes both to the same value, so `starts_with` trivially always succeeds regardless of any symlink underneath. Fix: when the configured root is file-shaped, check the candidate against the root's parent directory instead of the root itself (at the `check_for_new_sessions`/`open_read_only` call site), keeping a real directory boundary.
